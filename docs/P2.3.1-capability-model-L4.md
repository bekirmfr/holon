# P2.3.1 — Capability model · Level-4 design

> *pre:* P2.1.1, P2.2.1 · *inv:* `I7` / `I8` · *projects to:* P2.3.2 (union) · *effort:* **M**
> *References row:* I8 / P2.3 — port Unison abilities' *union-of-callees, surface-before-use*;
> diverge on **no discharge** (`REFERENCES.md`).

The flagged L4 decision is exactly one thing: **enumerate the capability set** — a
design choice the way the primitive set was. Everything else (sourcing, fail-closed,
the union) reuses machinery `kind` already established. So this note spends its budget
on the set and on one structural decision the set forces: the relationship between
*capabilities* and the *kind* we already built.

---

## 0. The decision that matters: capabilities are primary, kind is their projection

The plan says it in one line — *"kind is the four-bucket projection of this: 'has any
irreversible capability' ≈ Sink."* Taken seriously, that settles an architecture:

**Capabilities are the primary classification; kind is a derived view of them.** Kind
is coarse (4 buckets); capabilities are fine. You can project fine → coarse, never the
reverse. By the project's deepest rule — *derivable ⟹ derived, never asserted* — kind
must therefore be **computed from** capabilities, not classified independently
alongside them. Two parallel tables could drift; a projection-by-construction cannot.

The motivating case is sharp and real. `Clock` and `SecretAccess` **both** project to
`Driver` (both read the world). But a consent gate must distinguish *"reads the
current time"* from *"reads your credentials"* — and kind cannot, because it threw that
away in the projection. **That gap is the entire reason capabilities exist.** Kind
answers "is it safe to run blindly?"; capabilities answer "what exactly will it
touch?" — and the second is the question a human approves an import on.

**Consequence for what we already built.** This *reframes* P2.2.1 rather than sitting
beside it: `effects_of`'s leaf contribution should come from *projecting*
`capabilities_of`, not from a standalone `kind_of`. For the current vocabulary this is
**behaviour-preserving** — the projection reproduces P2.2.1's exact table
(`email → {Sink}`, `store → {State}`, `timer → {Driver}`, pure → ∅) — so it is a
source refactor with identical outputs, provable by the existing `effects_of` tests
staying green. (See §4 for the precise staging, and the one honest wrinkle: a leaf may
in principle touch *several* axes, which makes a leaf's kind properly a *set* too.)

## 1. The capability set (the enumeration)

**Atomic now, parameterized later.** A capability is a *category* of touch
(`NetworkEgress`), not yet the *resource* it touches (`NetworkEgress("api.evil.com")`).
The resource parameter is a precision upgrade that (a) needs `capabilities_of` to read
the unit's *params*, and (b) raises a static-vs-dynamic question (the destination is
often a runtime input, not knowable before import). It is deferred (§7) — atomic
capabilities already deliver the enumeration, the non-laundering property, and a
consent surface that says *"sends on the network, reads files, accesses secrets."*

The enumerated set, organized by the kind each member **projects to**:

| Capability | Projects to | Touch |
|---|---|---|
| `Clock` | Driver | reads wall-clock / timers |
| `NetworkIngress` | Driver | receives inbound data / requests |
| `FileRead` | Driver | reads external file state |
| `SecretAccess` | Driver | reads a secret / credential *(security-flagged)* |
| `Random` | Driver | sources entropy / nondeterminism |
| `StateRead` | State | reads value retained across firings |
| `StateWrite` | State | writes value retained across firings |
| `NetworkEgress` | Sink | sends outbound (mail, HTTP write) |
| `FileWrite` | Sink | writes / deletes files |
| `Spawn` | Sink | starts a process / job |

The projection rule is one fixed tag per capability — `Capability::kind() -> Kind` —
and is deliberately lossy: *read-the-world* → `Driver`, *retain* → `State`, *commit
irreversibly* → `Sink`. `Capability::kind()` never returns `Pure`; **purity is the
empty capability set** (exactly as `Effects` already encodes it).

**Enumerate the whole set now; classify only what exists.** The `Capability` enum
fixes the design decision. But `capabilities_of` need only map the *current* exemplars
(`email`, `store`, `timer`) plus pure → ∅; the rest are reserved names that the
corresponding effect leaves register as they are built — mirroring how P2.1.1 fixed the
pure vocabulary and left the effectful vocabulary to fill in.

## 2. The functions and signatures

```rust
/// A category of effect — what a leaf touches outside its inputs. Atomic for now
/// (no resource parameter; see §7). Ordered for deterministic set storage, same
/// disclaimer as Kind: storage order, not a danger ranking.
pub enum Capability {
    Clock, NetworkIngress, FileRead, SecretAccess, Random, // → Driver
    StateRead, StateWrite,                                  // → State
    NetworkEgress, FileWrite, Spawn,                        // → Sink
}

impl Capability {
    /// The coarse kind bucket this capability projects to. Never Pure.
    pub fn kind(self) -> Kind { /* fixed tag per variant */ }
}

/// The capability manifest of a primitive leaf, by name. Mirrors `kind_of`:
/// - pure leaf  ⇒ Some(∅)   — the positive "touches nothing outside its inputs"
/// - effectful  ⇒ Some({…}) — its declared capabilities
/// - unknown    ⇒ None      — fail closed (caller treats as maximal)
pub fn capabilities_of(name: &str) -> Option<Capabilities>;
```

`Capabilities` is the same newtype shape as `Effects` — a `BTreeSet<Capability>` with
`is_empty`/`contains`/`iter`, `∅ ⇒ pure`, a *may-touch upper bound*. The union over a
closure (P2.3.2) is the **identical fold** as `effects_of`, with `Capability` swapped
for `Kind` — which is why P2.3.2 is buildable at L3 with no separate descent.

## 3. Sourcing & fail-closed (reused, not reinvented)

Identical discipline to `kind`, because it is the same trust problem:

- **Closed core table.** `capabilities_of` is a core-resident match over the trusted
  leaf set. Leaves are closed (the marketplace ships only composites, which *derive*);
  new effect leaves are trusted host releases that add their row here.
- **Declaration in core, execution in host.** Core *declares* `email`'s
  `NetworkEgress`; the host *performs* it. The capability table is the trust basis the
  surface reads; the host's trusted leaves honour it.
- **Fail-closed.** Unknown leaf ⇒ `None` ⇒ the closure saturates to all capabilities
  (the `Capabilities` analogue of `effects_of`'s saturation). Never silently ∅.
- **Real units only.** Capabilities are derived from the *real* leaves, never mocks
  (the P2.7 guardrail) — design mode can simulate innocence, but the surface still
  reflects what *deploy* will do.

**Declaration + surfacing, not enforcement.** P2.3.1 makes the manifest *derivable and
visible*; it does not *sandbox* execution to block an undeclared effect. Enforcement
presupposes untrusted leaf execution, which does not exist (leaves are trusted
syscalls). Capability-secure execution is a much larger, separate concern (§7).

## 4. The kind refactor — staging

Recommended: **Staging α (unify now)**, because it closes the drift window immediately
and is behaviour-preserving for the current vocabulary.

- `effects_of`'s primitive branch changes from "`match kind_of(name)`" to
  "`match capabilities_of(name) { Some(caps) => insert each caps.kind(); None => saturate }`".
  A pure leaf returns `Some(∅)` ⇒ contributes nothing ⇒ pure; identical output.
- `kind_of(name) -> Option<Kind>` becomes the **single-bucket projection** of
  `capabilities_of` (for the current ≤1-axis leaves it returns exactly today's value).
  P2.1.1's tests stay green.

The honest wrinkle to record: once a leaf exists that touches *several* axes (e.g. a
hypothetical `FileRead` + `FileWrite` leaf ⇒ `{Driver, Sink}`), a leaf's kind is
properly a **set**, and the single-`Kind` `kind_of(name)` convenience yields to
`Effects` at that point. No current leaf is multi-axis, so the convenience holds for
now and we do not pre-build for the case.

*Alternative — Staging β (parallel, unify at P2.3.2):* add `capabilities_of` beside an
untouched `kind_of`, with a *tested* consistency invariant, and fold the unification
into P2.3.2. KISS-er this inch, but it opens a (test-guarded) drift window and defers
the principled "derived, not asserted" wiring. **α preferred**; β recorded.

---

## 5. Surface before import (P2.3.2, previewed)

P2.3.2 is the payoff and is the `effects_of` fold reused: `capabilities(unit,
resolver) -> Capabilities`, union over `children ∪ hash-valued params`, fail-closed,
**computed not stored**. The governing test: a `NetworkEgress` buried deep in a
closure surfaces at the top *before* the unit is run or imported — *nothing
exfiltrates silently* (I9). This is the property the prior-art reviews single out as
Holon's defensible center, and it is exactly Unison's "ability requirement propagates
into the signature" — ported, with our *no-discharge* divergence.

## 6. Prior art & divergence

- **Unison abilities** — required set = union of callees, surfaced before use. Ported
  as the inference shape. **Diverge: no discharge** — no handler removes an axis;
  effects are observable; only design-mode mocks are handler-like, and they are
  trust-excluded.
- **Roc platforms / managed effects; object-capability model (E, Pony, Newspeak)** —
  the "capability as an explicit, surfaced manifest of what code may touch" idea.
  Ported as the manifest concept. Diverge: ours is *derived from graph structure*, not
  *granted by a handle passed at call*.
- The capability-vs-kind split is the standard *fine effect set vs coarse summary*
  pattern (Koka/Eff rows vs a top-level effect annotation).

## 7. Sub-leaves (build order)

1. **`Capability` enum + `Capability::kind()`** — fix the enumerated set and the
   projection tags. (Add `PartialOrd, Ord` for `BTreeSet`, same disclaimer as `Kind`.)
2. **`Capabilities` newtype** — mirror `Effects` (`is_empty`/`contains`/`iter`, ∅⇒pure).
3. **`capabilities_of(name)`** — closed core table: pure ⇒ `Some(∅)`; `email` ⇒
   `{NetworkEgress}`; `store` ⇒ `{StateRead, StateWrite}`; `timer` ⇒ `{Clock}`;
   unknown ⇒ `None`.
4. **Refactor `effects_of` leaf branch to project `capabilities_of`** (Staging α;
   behaviour-preserving) and redefine `kind_of(name)` as the single-bucket projection.

(P2.3.2 — `capabilities(unit, resolver)` union — follows as its own inch, the
`effects_of` fold with `Capability`.)

## 8. Tests (the proofs)

- `pure_leaf_declares_empty` — `capabilities_of("add") == Some(∅)`; positive emptiness,
  not `None`.
- `effectful_leaves_declare_caps` — `email ⇒ {NetworkEgress}`, `store ⇒ {StateRead,
  StateWrite}`, `timer ⇒ {Clock}`.
- `projection_reproduces_kind` — for every exemplar, projecting its caps yields its
  P2.2.1 kind (the behaviour-preserving proof).
- `fine_distinguishes_what_coarse_loses` — `Clock` and `SecretAccess` **both**
  `.kind() == Driver`, yet are distinct capabilities (the motivating case: kind is
  lossy, capabilities are not).
- `capability_kind_is_never_pure` — `Capability::kind()` ∈ {Driver, State, Sink}.
- `unknown_leaf_has_no_manifest` — `capabilities_of("frobnicate") == None`, and
  `effects_of` over a closure containing it still saturates (fail-closed preserved).
- `effects_of_outputs_unchanged` — the existing `effects_of` suite stays green after
  the α refactor (identical sets).

---

## 9. Deferred forks (recorded)

- **Parameterized resources** — `NetworkEgress(host)`, `FileRead(path)`,
  `SecretAccess(name)`. Needs `capabilities_of` to read the unit's *params* and a
  `Resource = Static(value) | Dynamic` model (the destination is often a runtime input,
  unknowable before import — surface *"sends to api.stripe.com"* vs *"sends to a
  runtime-determined host"*). A precision layer over this structure, not a change to it.
- **Capability enforcement / sandboxing** — execution that *blocks* an undeclared
  effect. Presupposes untrusted leaf execution; leaves are trusted syscalls today, so
  this is out of scope until (if ever) untrusted native leaves exist.
- **Multi-axis leaf ⇒ leaf-kind-as-set** — retire the single-`Kind` `kind_of(name)`
  convenience when the first such leaf appears (§4).
- **Consent-gate UX** — how the surfaced manifest is presented for approval at import
  is an Editor (P4) concern; here we only make it *derivable*.
