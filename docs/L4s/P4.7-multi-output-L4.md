# P4.7 — Native multi-output · Level-4 design note (rev 2)

> **Companion to `PLAN.md`.** Lets a `Unit` expose several distinct outputs natively — the
> concrete need is a MACD-style indicator (a line, a signal, a histogram), but the shape is
> general: any unit with more than one meaningfully separate result. **Pre:** P1.4.3 (eval),
> P1.5.1 (encapsulation), P3.3.2 (shared cache), P4.1 (authoring canvas, done), P4.3
> (encapsulation UX — sequencing note in §7). **Inv:** I1, I2, I3, I5, I6. **Effort:** L.
>
> Per the L4-readiness rule (`PLAN.md`): this leaf needs a design note because it is large
> *and* hides a genuinely unresolved sub-decision (§3.2) — unlike P4.3, whose one real
> decision was resolvable inline in its L3 spec.

---

## 0. Why this needs its own note, precisely

Multi-output was named a **deliberate, recorded deferral** at the very first evaluator
design, not an oversight discovered later:

> *"Single output (port 0). Multi-output composites are a recorded deferral (design doc
> §9); the `Edge.from_port` field already allows it structurally for later."* — P1.4.3

> *"Single exposed output falls out of the duplicate rule... Multi-output stays deferred."*
> — the journal entry when validation was built

So the wire *format* was built with room for this on purpose. What's missing is real work in
four places, not a flag to flip: `Unit`'s own shape, `eval`'s core signature, memoization's
cache format, and the editor's fundamentally single-output-handle wiring model. This note
exists to settle the one genuine fork before touching any of them.

---

## 1. Grounding — what exists today, read directly, not assumed

**`Unit.output: Option<Type>`** — one type, or none (a driver-leaf placeholder). Everywhere
this is read, it's read as a singleton.

**`eval(unit: &Unit, inputs: &[Option<Value>], resolver: &impl Resolver) -> Option<Value>`**
(`eval.rs`). The two places a child's *output* gets read already discard the very field that
would matter for multi-output:

```rust
// eval_composite, reading another child's already-evaluated output:
Some(&(fc, _fp)) => scratch[fc as usize].clone(),   // line 89 — from_port discarded
// reading the composite's OWN exposed output:
Some(&(fc, _fp)) => scratch[fc as usize].clone(),   // line 105 — same discard
```

Compare the sibling line reading a promoted *input*, four lines above the first: `Some(&
(BOUNDARY, fp)) => inputs.get(fp as usize)...` — `fp` is used there, because inputs are
already multi-slot. This is the exact asymmetry multi-output closes, and it's already
pinpointed to two lines, not a vague "somewhere in eval."

`scratch: Vec<Option<Value>>` is indexed **by child**, one slot each — it has nowhere to put
a second value for a child that has one.

**`validate.rs`** hardcodes port 0 on both the source and destination sides of an output
read:

```rust
// reading a child's output as an edge source:
Some(src) => match (e.from_port, &src.output) {
    (0, Some(t)) => t.clone(),
    _ => { errors.push(ValidationError::OutputPortOutOfRange { .. }); }
}
// reading the composite's own output via a boundary-sink edge:
match (e.to_port, &unit.output) {
    (0, Some(t)) => t.clone(),
    _ => { errors.push(ValidationError::BoundaryOutputOutOfRange { .. }); }
}
```

**`encapsulate.rs`** — `EncapSpec.output: (u32, u32)`, one `(child, port)` pair.
`derive_and_freeze` accepts only `(_, 0)`. `default_spec` computes the *full* candidate list
of free (unconsumed) outputs already, checks its length, and — until this session's
error-surfacing inch — discarded it:

```rust
let mut free: Vec<u32> = (0..k as u32)
    .filter(|c| !consumed.contains(c) && resolved[*c as usize].output.is_some())
    .collect();
if free.len() != 1 {
    return Err(EncapError::AmbiguousDefaultOutput(free)); // the list is already right here
}
```

**`memo.rs`** — `CacheEntry { unit_hash: Hash, inputs: Vec<Option<Value>>, output: Value }`.
`memo_key` already encodes `inputs: &[Option<Value>]` slot-by-slot (`SLOT_ABSENT`/
`SLOT_PRESENT` + `encode_value`) — the exact mechanism a `Vec<Option<Value>>` of *outputs*
would need, already written, just not yet called on the output side.

**The editor** (`PrimitiveNode.tsx`) renders exactly one output row; `App.tsx`'s wiring
(`isValidConnection`, `onConnect`, the `wedges` builder in `onProject`) hardcodes
`from_port: 0` at every wire-construction site, mirroring the exact same "port 0 only"
assumption core carries.

**Kind/capability classification (`kind.rs`)** is provably untouched: `collect_caps`, the one
function every derivation runs through, walks a primitive's *name* and `child_refs` (hash
references) — no code path reads `Unit.output` or a port count at all. Confirmed by reading
the function, not inferred from its purpose.

**`holon-host`'s firing loop (added on review — missing from rev 1's grounding, which is
exactly what produced rev 1's weaker reasoning in §5).** `perform_effects` walks only the
value `eval` returns for the exposed boundary — `Value::Effect` performs, `Value::List`
recurses (already-solved multi-effect fan-out, §5), anything else "carries nothing to
perform." Nothing internal that isn't wired to the exposed output is ever examined. This is
named, not incidental: *"An effect is a value that reaches the output... a request actually
fires only when it reaches the output. A buried request that is wired nowhere is dead code —
computed and discarded — and correctly does nothing. May ≠ does, and that distinction is
right, not a gap."* (`P2.4.1-firing-loop-L4.md`). This directly decides §5's fork.

## 2. The shape

**`Unit.output: Option<Type>` → `Unit.outputs: Vec<Port>`.**

Not `Vec<Type>` — `Port { name: String, ty: Type }`, the exact type `inputs` already uses.
This is a real, deliberate choice, not the path of least typing: a MACD unit's three outputs
benefit from names ("macd_line", "signal", "histogram") for the identical reason inputs
already carry names, and it makes `outputs` structurally symmetric with `inputs` rather than
a second, differently-shaped concept living beside it.

**`EncapSpec.output: (u32, u32)` → `EncapSpec.expose: Vec<Expose>`**, where `Expose { child:
u32, port: u32, name: String }` — the exact shape `Promote` already has for inputs, applied
to the output side. Order is identity, same as `promote` already is.

**`default_spec`'s output rule generalizes from "the one free output" to "every free output,
in canonical `(child, port)` order, each named after its inner port"** — exactly mirroring
how it already promotes every unbound *input* with zero ambiguity-checking. This is not a new
idiom; it's applying the one that already exists for inputs to the side that didn't have it.

**`validate.rs`'s two hardcoded `(0, Some(t))` matches become `outputs.get(port as usize)`** —
mechanical, but exact: `OutputPortOutOfRange`/`BoundaryOutputOutOfRange` now fire when `port
>= outputs.len()`, not when `port != 0`.

## 3. The one real fork

### 3.1 What's *not* actually in question

Whether `eval`'s signature needs to change at all — it does, unavoidably, once a unit can
have more than one output. What it changes *to* is the fork.

### 3.2 `eval`'s new return shape: `Vec<Option<Value>>`, and why not the alternative

Two candidates:

- **`Vec<Option<Value>>`** — per-output, independently present or absent.
- **`Option<Vec<Value>>`** — the whole unit succeeds or it doesn't; if it does, every output
  is present.

**Recommendation: `Vec<Option<Value>>`.** Reasoning, grounded in the actual evaluator
internals above, not abstract preference:

`eval_composite`'s `scratch` is *already* `Vec<Option<Value>>`, one slot per child, precisely
because a child's readiness is evaluated independently of its siblings — that's the entire
point of the topological pass. Generalizing each child's slot to hold `Vec<Option<Value>>`
(one `Option` per that child's own output count) is the **minimal, structurally consistent**
extension: it reuses the exact None-propagation idiom already proven for inputs, rather than
introducing a second, all-or-nothing failure concept that inputs don't have. A composite
exposing two different children's outputs, where one child hits a divide-by-zero and the
other doesn't, has a real, principled answer under this model (the good one is present, the
bad one is `None`) and no clean answer under the alternative (the whole exposed tuple
collapses to nothing, discarding a value that was genuinely computed).

**The honest cost, stated plainly, not minimized:** every existing caller of `eval` —
composite recursion, `memo.rs`'s `verify_entry`, `simulate.rs`'s `design_eval`, the wasm
bridge, every test — currently expects a bare `Option<Value>` and needs to change. This is a
real, pervasive ripple, not a contained one. It is not avoidable by keeping the old signature
for single-output units and adding a parallel `eval_multi` for the rest — that would be two
deciders for "what does running a unit mean," exactly the duplication this whole project has
consistently refused elsewhere (one evaluator, one type-checker, one interface-deriver). The
ripple is the honest price of doing this once, correctly, rather than the price of a shortcut.

A small ergonomic convenience is worth adding once the ripple lands: `eval_one(unit, inputs,
resolver) -> Option<Value>` = `eval(...).into_iter().next().flatten()`, for the (still very
common, even after this) single-output call sites that don't want to think about a vector.

## 4. Memoization

**`CacheEntry.output: Value` → `CacheEntry.outputs: Vec<Option<Value>>`** — matching `eval`'s
own return shape exactly, not a narrower "all present" requirement invented to make caching
simpler. In a pure system, "output slot 1 is always `None` for these inputs" is just as
stable and cacheable a fact as any concrete value; forcing every slot to be present before an
entry can be filed would be an artificial gate on top of a system that doesn't need one.

**No new encoding tag needed.** `memo_key` already encodes `inputs: &[Option<Value>]`
slot-by-slot (`SLOT_ABSENT` / `SLOT_PRESENT` + `encode_value`, per-slot). That loop is exactly
what `outputs` needs too — factor it into one shared helper (`encode_slots`) called from both
`memo_key` (inputs) and the extended `entry_key`/`verify_entry` (outputs), rather than writing
a second version of a loop that already exists.

## 5. Invariant audit (re-run against the real code this time, not just the design's intent)

- **I1 (parity)** — `eval` is still the one entry point for primitive and composite alike;
  multi-output doesn't add a second evaluation path, it widens the one that exists.
- **I2 (purity)** — unaffected; `eval` returning several values instead of one is still a
  deterministic function of `(unit, inputs)`.
- **I3 (composition by reference)** — untouched; this is about a unit's own interface, not how
  it references children.
- **I4 (derive-then-freeze)** — strengthened, not bent: `Unit.outputs` gets the *same*
  treatment `inputs` already has (derived types, chosen names/order, frozen into the hash).
  The old single-output model was the asymmetric special case; this makes the two sides
  consistent.
- **I5 (identity = structure)** — the *order* of exposed outputs becomes part of identity,
  exactly as promoted-input order already is. Confirmed directly: `derive_and_freeze`'s
  `order_is_identity` test already proves this for inputs; the same claim needs the same test
  for outputs once built.
- **I6 (closure/pinning)** — untouched; keyed off child references, not output count.
- **I7/I8/I9 (capability, derived labels, inspect-to-leaves)** — confirmed by directly reading
  `collect_caps`: it never touches `Unit.output`/`outputs` or a port count. Nothing here
  changes.

**The one real behavioral change, named plainly:** `EncapError::AmbiguousDefaultOutput`
*partially* dissolves. "Two or more free outputs" stops being an error and becomes "expose
them all" — the exact same non-error `default_spec` already applies to unbound inputs.

**"Zero free outputs" does not dissolve the same way, and now for a grounded, specific
reason rather than "no example comes to mind."** The obvious counter-proposal — a composite
that performs an effect and exposes nothing, a "fire and forget" sink — turns out not to
work under this system's own, already-decided effect model. `holon-host`'s firing logic only
performs what it finds by walking `&output`, the value `eval` returns for the exposed
boundary:

```rust
fn perform_effects(value: &Value, host: &mut impl Host) {
    match value {
        Value::Effect { sink, payload } => { /* host.perform(...) */ }
        Value::List(items) => { for item in items { perform_effects(item, host); } }
        _ => {} // pure data at the root carries nothing to perform
    }
}
```

This is a named, deliberate design decision, not an accident — the firing-loop's own design
note states it directly: *"An effect is a value that reaches the output... a request
actually fires only when it reaches the output. A buried request that is wired nowhere is
dead code — computed and discarded — and correctly does nothing. May ≠ does, and that
distinction is right, not a gap."*

So a zero-output composite wrapping a sink would construct the effect internally and then
silently discard it — never performed. A sink-only unit doesn't want *zero* outputs; it
wants exactly the one it already has today, the constructed `Effect` itself. That's not "no
meaningful output" — the output *is* the point, data that happens to be a request rather
than a number.

**Worth stating plainly since it clarifies the whole leaf: multi-output and "I want to
perform several effects" are unrelated.** `perform_effects` already recurses into
`Value::List`, so `map(egress, xs)` or a hand-built list of effects already fans out several
effects through one output — solved, and untouched by this note. Multi-output's actual value
is exposing several distinct, independently-typed *data* values (MACD's three series), not
effects.

**Recommendation, now grounded rather than merely cautious: keep "zero free outputs" an
error.** Not because no one has thought of a use case, but because the one obvious candidate
use case — a pure-effect, no-return unit — is actively broken by this architecture's own
"effects exit at the bottom" invariant, which this note has no reason to touch or override.
`AmbiguousDefaultOutput([])` stays exactly as this session's error-surfacing inch already
built it, now firing only for the empty case (never for "≥2", which becomes the non-error
"expose all").

## 6. What the editor needs (design-level only — its own sub-inch, not detailed here)

`PrimitiveNode.tsx`'s output column currently renders one row; it becomes a `.map()` over
`outputs`, exactly mirroring how the *input* column already maps over `inputs` — the same
idiom, not a new one. Every wire-construction site that currently hardcodes `from_port: 0`
(`App.tsx`'s `isValidConnection`, `onConnect`, the `wedges` builder in `onProject`) needs
`from_port` resolved from the *source* handle's index into the source node's own `outputs`,
mirroring exactly how `to_port` is already resolved from the target handle's name via
`.findIndex(...)` on the target's `inputs`. Mechanical once the input-side pattern is the
template, but real UI work, not a config flag.

## 7. Sequencing against P4.3

These two leaves touch overlapping surface (`EncapSpec`, `default_spec`, `derive_and_freeze`,
the `project()` bridge) but are **orthogonal decisions**: P4.3's "let the UI choose which
output to expose" is still meaningful, and still single-output-at-a-time, even without
native multi-output — picking *one* candidate from `AmbiguousDefaultOutput`'s list doesn't
require a unit to ever expose more than one thing at once. Neither blocks the other. Given
they touch the same files, doing P4.3's bridge split *after* this lands would mean writing the
split once against the final `EncapSpec` shape rather than twice — a sequencing preference,
not a dependency.

## 9. Tests (the proofs, not yet written)

- **Behavior preservation, the key one:** every existing single-output unit evaluates
  identically under the new shape (`eval(...)[0]` equals the old `eval(...)`) — multi-output
  changes the *contract*, not the answer, for anything that only ever had one output.
- **A genuine multi-output round trip:** a unit with three outputs, wired so two are consumed
  internally and one is exposed alongside two fresh ones from other children — projects,
  evaluates, and each exposed slot carries the right value.
- **Partial success:** two exposed outputs from two different children, one hitting a
  divide-by-zero — the good one is `Some`, the bad one is `None`, independently.
- **`order_is_identity`, extended:** two specs exposing the same outputs in different order
  hash differently — the same test `derive_and_freeze` already has for inputs, mirrored.
- **§5's resolution:** `AmbiguousDefaultOutput([])` still fires when zero children have a free
  output; `AmbiguousDefaultOutput` never fires for "≥2" any more (that becomes the non-error
  "expose all"). A companion test worth adding alongside it: a composite wrapping only a sink
  leaf, with that leaf's `Effect` output left unexposed, correctly still reports zero free
  outputs as an error — proving the "fire and forget" shape stays caught, not silently allowed
  through by an unrelated code path.
- **Memo round-trip:** a `CacheEntry` with a partial (`Some`/`None` mixed) outputs vector
  verifies correctly via re-execution, the same way `nan_output_verifies_canonically` already
  proves a single-output edge case today.

---

## 10. Deferred, named rather than silently dropped

- **Named-field access on outputs** (`macd.histogram`-style) — outputs are positional-with-a-
  name for display, not a `Record`; the same deferred fork as `Product`'s own field naming.
- **`Filter`/`Reduce`-style higher-order primitives interacting with multi-output units** — out
  of scope; `map`/`fold` are not touched by this note and aren't assumed to generalize for
  free.
- **The P4.3 bridge split itself** — sequenced after (§7), not part of this leaf.
