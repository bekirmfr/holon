# L4 — the browser↔host transport (scoping, before any code)

**Status:** scoping note, not a build. Grounded fresh against the real current
`holon-host/src/lib.rs` (not assumed from the handoff's description) before writing this. This is
what unblocks `P4.5.1` (Registry client) and `P4.6.1`'s deploy half at once.

---

## 1 · What already exists (re-grounded, not assumed)

- `Store` (trait): owned `put`/`get` by hash, `MemStore` + on-disk `FileStore`. Every read is
  **verify-on-read** (`decode_verified`: decode, re-hash, reject on mismatch) — this is
  synchronous, in-process Rust today, no network.
- `Registry<S: Store>`: `publish` (walks the closure via `child_refs`, fails closed on any
  dangling reference, else commits + records the hash), `is_published`, `published()`, `fork`.
  Also synchronous, in-process.
- `SharedCache`: `put` (derives its own key), `get` (unverified fast path), `get_verified`
  (re-executes — the trustless read), and `ingest(claimed_key, entry)` — the one piece already
  built *for* a network boundary (P3.8.2's finding: a peer-supplied entry is admitted only if it
  hashes to the key it claims).
- `fire`/`fire_sourced` (`Host` trait): the one genuinely impure function in the whole system —
  `Host::perform`. Also synchronous.
- **None of this is reachable from `holon-wasm` today.** The wasm crate depends on `holon-core`
  only (Cargo-enforced); `holon-host` has never been asked to compile to `wasm32` and doesn't need
  to — the point of a transport is precisely to avoid that, since `Store`'s `FileStore` uses
  `std::fs`, which has no browser meaning anyway.
- There's a standing L4, `P3.8.2-transport-L4.md`, already on record with the load-bearing finding
  for this whole problem: **the security of a network boundary here is already fully provided by
  content-addressing.** A stranger's claimed bytes/key/result are each independently checkable
  (`decode_verified`, `entry_key`, `verify_entry`/`get_verified`) without trusting the stranger.
  That L4 explicitly deferred **only the wire itself** — "a different kind of work (large dep
  surface, async I/O, untestable in this crate's pure-unit-test discipline)."

**What this means for scope:** the transport layer being scoped here is *not* a new trust
mechanism. It is the plumbing that lets a browser reach code that already knows how to say no to a
liar. Reaching for auth, sessions, or accounts here would be exactly the kind of hedge the project's
own discipline forbids — the property ("can I trust what I got back") is already provided; a
transport only needs to move bytes and re-expose the checks that already exist.

---

## 2 · The actual question: a service running where, speaking what, reached how

**Where.** The simplest thing that solves "a browser tab needs to call into `Store`/`Registry`/
`fire`" is: a small **local HTTP server**, a new thin binary (or a `[[bin]]` target) that links
`holon-host` and does nothing but wrap its existing calls behind endpoints. Not a daemon, not a
cloud service — a process the user starts alongside `npm run dev`, listening on `127.0.0.1`.

**Why not something heavier.** `Store`/`Registry`/`fire` are synchronous, request/response,
low-volume (a human clicking "publish" or "import," not a stream). That's an ordinary REST-shaped
problem. Reaching for WebSockets, gRPC, or an async runtime would be adding machinery the actual
usage pattern doesn't need — none of P4.5.1's or P4.6.1's own leaf definitions describe anything
that needs a persistent connection or push updates.

**Speaking what.** JSON over HTTP. `holon-wasm` deliberately avoids `serde` in `holon-core` to keep
the pure crate dependency-minimal — but that constraint is about `holon-core`, not `holon-host`,
which is already the impure shell and already free to take dependencies wasm can't. A JSON layer
here is the same shape of decision the wasm bridge already made for `Value` (serde-wasm-bindgen at
that boundary; ordinary serde here), not a new precedent.

**Reached how (CORS).** The dev server (Vite) and this new local server are different origins
(different ports), so the server needs to send permissive CORS headers — scoped to `localhost`
origins only, not `*`, since the one open question below is exactly whether this ever needs to be
reachable from anywhere else.

### Proposed endpoint shape (thin wrappers, not new logic)

| endpoint | wraps | notes |
|---|---|---|
| `GET /unit/:hash` | `Store::get` | verify-on-read already inside |
| `POST /unit` | `Store::put` | returns the hash |
| `POST /registry/publish` | `Registry::publish` | fails closed on dangling refs, as today |
| `GET /registry` | `Registry::published()` | list |
| `POST /registry/fork` | `Registry::fork` | |
| `POST /cache/:key` (verified read) | `SharedCache::get_verified` | |
| `POST /cache/ingest` | `SharedCache::ingest` | the P3.8.2 gate, exposed |
| `POST /fire` | `fire`/`fire_sourced` | **this is `P4.6.1`'s deploy half** — the one endpoint that performs a real effect, so it's the one worth the most scrutiny in review |

Every endpoint is a direct call into code that already exists and is already tested. No new
decision logic lives in the server — same discipline as "the editor invents almost nothing," now
applied to this new binary: it's a *transport*, not a second implementation of anything.

## 3 · Open forks — surfacing rather than picking silently

### Fork 1: is this ever meant to be more than localhost?

This is the one that actually changes the design, not just the deployment:

- **If localhost-only, forever (a local dev/companion process):** the above is close to done —
  CORS locked to `localhost` origins, no auth needed (content-addressing already secures *what*
  you get; there's no *who* to gatekeep on a single-user local process), `MemStore`/`FileStore`
  exactly as they are today.
- **If this is meant to ever be a real shared/networked registry (the actual marketplace, reachable
  by strangers):** content-addressing still secures correctness, but a public write endpoint
  (`POST /unit`, `POST /registry/publish`) becomes a spam/flood vector that identity-free trust
  doesn't address by itself — rate-limiting or proof-of-work-style admission control becomes a real
  question, not a hedge. That's a materially bigger scope than P4.5.1/P4.6.1 need today.

My read: **P4.5.1 and P4.6.1's own leaf definitions only need localhost** (they're editor
features — import/publish/deploy from the person's own machine). Building for the networked case
now would be scope creep against leaves that don't ask for it — the project's own "build the least
the architecture needs" principle points at localhost-only. But this is a real fork, not a
formality, so I'm asking rather than assuming.

**Resolved (2026-07-02, user decision): local registry first.** Build the local HTTP server
against the existing `Store`/`Registry` as they stand today; unblocks `P4.5.1`/`P4.6.1` immediately.

**The "same interface as the eventual external registry" requirement is already satisfied, and
needs no new design.** `Registry<S: Store>` is already generic over `Store`
(`put(unit) -> Hash` / `get(hash) -> Option<Unit>`); nothing about `Registry::publish`/`fork` or
the HTTP endpoints wrapping them needs to know what backs `Store`. Keep the endpoint layer as thin
wrappers over `Store`/`Registry` exactly as written today, don't let endpoint code assume
local-file specifics, and the "swap the backend later" property is inherited from code that
already exists — not something to design now.

**A DHT/bootstrap-node discovery layer was considered and deliberately deferred, not built.**
No current leaf needs peer discovery (`P4.5.1`/`P4.6.1`'s own test criteria are both satisfiable
locally). This echoes a decision already on record in `P3.8.2-transport-L4.md`, which named a
`Remote`/`Peer` trait "speculative until a 2nd transport." A DHT is one specific, heavy answer
(bootstrap nodes, peer discovery, NAT traversal, typically a large dependency like `libp2p`) to a
question — how do strangers find each other — that no leaf has yet asked in a way that prefers it
over simpler answers (e.g. a small federation of known HTTP registries). Nothing is lost by
deferring: `Store` is already hash-keyed get/put, which a Kademlia-style DHT (also natively
content-hash-keyed) or a federated `Store` could each satisfy as just another `impl Store`,
without the wire/endpoint layer above it changing. When a leaf genuinely needs cross-machine
discovery, that choice deserves its own grounded L4 at that time, not a default made now.

### Fork 2: does `P4.6.1`'s mock/stimulus editing touch this transport at all?

Tracing it through: `P4.6.1`'s custom mocks/stimuli are described in its own leaf as **ephemeral
test-context** that must affect a design-mode run but **never** the unit's hash. `design_eval` is
pure core, already resolver-substitution-based, and runs entirely client-side once the small
`#[wasm_bindgen]` wrapper exists (the leaf B from last turn). Nothing about grouping/expanding a
composite mid-session changes what gets resolved by hash — expand/group are canvas-only, cosmetic
operations that don't touch the underlying hashes at all (per the projection boundary already
established).

**Conclusion, not just a question this time:** mocks/stimuli don't need to reach this transport —
they're an editor-local substitution over hashes the editor already holds, same as `design_eval`
itself. This fork resolves to "no interaction, by construction," which also means Fork 2 doesn't
add scope to the transport layer. Worth stating plainly rather than leaving it looking open.

## 4 · What I'm NOT proposing

- No auth/identity layer — the architecture's whole thesis is trust-by-hashing; bolting on
  accounts here would be the exact "hedge against your own foundation" the project's discipline
  warns against, unless Fork 1 comes back "yes, networked," and even then the right tool is
  rate-limiting, not identity.
- No new async runtime in `holon-host` itself — a synchronous HTTP server (or a thin sync-over-
  blocking-threadpool one) is enough for this request pattern; don't reach for `tokio` because
  "servers usually do."
- No speculative `Remote`/`Peer` trait — already named as YAGNI in the P3.8.2 L4, still true here.

## 5 · Next step

Both forks are now resolved (§3). The concrete next inch: a new thin binary crate (name TBD, e.g.
`holon-server`) linking `holon-host`, with an HTTP framework dependency to pick (needs its own
small grounding pass — check what's actually in the sandbox's reachable registries, don't assume
a crate's current API from memory), wrapping the six endpoints in §2 as direct calls into
`Store`/`Registry`/`SharedCache`/`fire`, CORS-scoped to `localhost` origins only, no auth. `Store`
stays the one seam anything more distributed would plug into later — deliberately not built now.
That's a real, scoped, buildable inch.
