# Deploy-mode firing — Level-4 design (the host crossing)

> *crate:* **`holon-host`** — the first impurity; `holon-core` gains nothing for the
> minimal inch · *pre:* the Fork B reconciliation (sinks pure), `P1.4.3`, `P2.3.x`
> · *inv:* FCIS / `I5` / `§6` / `§7` · *effort:* **M**
> *References row:* P2.4 (FCIS/Roc; eager ⟹ quiescence free; **refuse debounce**).

This is the other half of `P2.4.1`. Design mode was pure `holon-core`; deploy mode is
where `holon-host` stops being a stub and the purity seam is crossed **once**, at the
host. Everything here builds on Fork B: a sink purely *constructs its request*, so the
pure graph already contains the answer to "what should happen" — the host only
*performs* it.

---

## 0. The seam: the host is the only impurity

```
   pure (holon-core)                    impure (holon-host)
   ─────────────────                    ───────────────────
   eval settles the graph  ──────────▶  Host::perform(capability, payload)
   → the request is OUTPUT DATA          → the one place IO happens
```

`eval` produces the request as ordinary output data (Fork B). The host reads it and
performs it. Nothing else in the system does IO. `holon-core` stays pure — no IO, no
async, no network deps, *ever*; `holon-host` depends on core and may grow them. The
crate graph **is** the purity boundary, enforced by Cargo, not by discipline.

---

## 1. The firing round (eager ⟹ quiescence is free)

```
source inputs ─▶ eval settles to a fixed point ─▶ perform the output's effect(s)
 (driver values)   (core — the one decider)         (host — the only impurity)
```

Because the round is **eager**, `eval` *returns* the settled value before anything is
performed — so no sink ever performs on a mid-propagation transient. There is nothing
to debounce; settle-then-perform is ordering, never a timer (refuse the sleep). For an
acyclic graph the fixed point **is** one `eval` pass, so each effect is performed once,
with its committed payload.

The round's full shape is Elm's `(Model, Cmd)`: *(state writes, effects to perform)*.
The **Cmd** half is this inch. The **Model** half (state) arrives with `P2.6.1` (§5).

---

## 2. Effects are output-carried — *not* collected from inside the evaluator

The one real design choice here, and it is forced by two commitments rather than taste.
A sink-bearing graph must hand the host *(capability, payload)* for each effect. Two
ways to get them:

- **(a) reach into `eval`** — an observer hook that fires as each sink node settles,
  capturing its payload at any depth.
- **(b) carry effects in the output** — the request the sink constructs flows to the
  graph's output as data; the host reads the output.

**Choose (b).** Two reasons make it not a preference:

1. **One evaluator (`I5`/P4.2).** (a) grows the evaluator a second responsibility and a
   hook every caller must reason about; (b) leaves `eval` exactly as it is. The editor's
   WASM `eval` and the host's native `eval` stay bit-identical.
2. **"Consequences exit at the bottom" (the doc's geometry).** An effect *is* a value
   that reaches the output. So the manifest's capability is the conservative **may**
   ("this graph can egress" — surfaced at any depth for trust, before import); a request
   actually **fires** only when it reaches the output. A buried request that is wired
   nowhere is dead code — computed and discarded — and correctly does nothing. May ≠
   does, and that distinction is *right*, not a gap.

So multiplicity rides the value model, which is exactly the **A → B** axis already
pinned:

- **A (now):** a single terminal sink — the output **is** the payload, and the manifest
  carries the one capability. The host performs `(that capability, output)`.
- **B (the upgrade):** `Value::Effect{capability, payload}` and `List[Effect]` at the
  output — computed, data-driven fan-out (`map → List[Effect]`, Elm/Roc `Cmd.batch`).
  Performed by iterating the output. Taken when the per-signup case is concrete.

Either way `eval` is untouched and the host stays thin. **No observer hook is built.**

---

## 3. The `Host` trait (impure, `holon-host`)

```rust
pub trait Host {
    /// Perform one settled request. The ONLY impure operation in the system.
    fn perform(&mut self, capability: Capability, payload: &Value);
    // later: fn drive(&mut self) -> Inputs;          // source real driver values
    // later: state read / write                       // P2.6.1
}
```

`perform` is where real IO lives in a real platform; a **recording host** (collects
`(capability, payload)` into a `Vec`) is the test double, so the whole loop is
sandbox-testable without touching the world. `drive` (sourcing real driver events) and
state are later seams — the minimal inch hands inputs in directly.

---

## 4. The firing loop (thin, `holon-host`)

```rust
pub fn fire(root: &Unit, inputs: &[Option<Value>], r: &impl Resolver, host: &mut impl Host) {
    if let Some(payload) = eval(root, inputs, r) {           // core settles the request
        for cap in capabilities(root, r).iter() {            // the manifest's effect(s)
            if cap.kind() == Kind::Sink {
                host.perform(cap, &payload);                 // the one impure act
            }
        }
    }
}
```

Minimal = the single-terminal-sink case: the settled output is the payload, the
manifest names the egress, the host performs it once. The loop is `eval` + `perform`;
it invents no evaluation. (Multi/dynamic effects are the **B** output-shape, not a loop
change.)

---

## 5. State — the `Model` half (P2.6.1; designed here, built after)

State is the one in-graph impurity the doc keeps. It does **not** fit the output-carried
effect model, because a state *read* needs the value from a prior round. So state is
**host-threaded**, in both modes:

- a state **read** is an *input* the host supplies (the current cell value) — like a
  driver, substituted in;
- a state **write** is a *consequence* the host persists — the `Model` half of the
  round's `(Model, Cmd)`.

This is why the round needs to surface *two* things (effects **and** state writes),
which in turn wants either multi-output composites (deferred, §9) or a structured round
result. Pinning that is `P2.6.1`'s job; the minimal effect-only loop above needs none of
it.

---

## 6. Build order

1. **Minimal host shell** *(holon-host — the impurity crossing)*: the `Host` trait,
   `fire` (single terminal sink), and a **recording host** test proving the effect is
   performed **once**, with the settled payload, and **only** at the host (core `eval`
   performed nothing). This is the inch that makes `holon-host` real.
2. **B — `Value::Effect` / `List[Effect]`** *(core + host)*: computed fan-out, when the
   per-signup case is concrete. The output-shape upgrade; the loop iterates it.
3. **State cell `P2.6.1`** *(core decl / host storage)*: host-threaded read/write; the
   `(Model, Cmd)` round.
4. **`drive`** — real driver sourcing (the host supplies inputs from the world).

---

## 7. Deferred (recorded)

- **Async + autonomous cells + settle/commit gate** → `P2.4.2` (eager makes it
  unnecessary now; never a debounce).
- **Effect contracts** — idempotency key `P2.5.2`, correlation token `P2.5.1`,
  transactional read-then-write `P2.6.2`.
- **Shared-sink multiplicity** — a sink reached by two parents: two firings or one?
  (Per-occurrence today; revisit with memoization.)
- **Real platform hosts** — an actual email/file/network `Host` impl; out of scope until
  there is a platform to target.
- **`Arc`/`Rc` value payload sharing** → `P3.3.1` (the `Arc`-vs-`Rc` choice depends on
  the host threading model decided here — single-threaded eager for now).

---

## 8. Invariant check

`I5` — **one evaluator**, untouched: no hook, no second traversal; `fire` calls the same
`eval`. `§7` — state remains the single in-graph place purity ends; effects are pure
data. FCIS — the host is the **only** impurity, and `perform` is the only impure
function. `§6` — eager settle-then-perform makes quiescence free; no debounce. The crate
graph (host → core, never reverse) enforces the boundary mechanically.
