# L4 · P2.5.1 — the correlation token (a boundary label, not an isolation engine)

> **Status:** design, pre-build. Resolves the explicit-vs-implicit fork and — more importantly —
> **relocates what the token is for.** Grounded against the one-way `Host` seam, the `Effect`
> payload, and the ingress/egress taxonomy. **No `Value`/`eval`/`hash` change.**
> **Pre:** Fork B (sinks pure), `drive` (sourced resolver), the value model's cleanliness.

---

## 1 · The leaf's question, and the trap in it

The leaf: *"a driver mints a token threaded through the graph so a response sink reaches the
right open caller; two concurrent requests get their responses routed correctly, none cross."*
Read naively, that asks for a **correlation/isolation engine** — machinery that keeps request A's
response from reaching caller B. That machinery is a trap, because **we already have it, for
free, and building it again would be the bad kind of duplication.**

---

## 2 · The insight: non-crossing is a theorem of purity, not a feature

Ask *how* two responses could ever cross. It requires a place where request A's data bleeds into
request B's path — i.e. **shared mutable state.** But the interior is pure. Two independent
requests flow down **independent data paths** with nothing to mix them; `eval` has no ambient
mutable context, no global, no hidden channel. The *only* point at which two requests can mix is a
**state cell** — and that is a merge the user deliberately wrote.

So "none cross" is not a guarantee the engine must add. It is the **same purity** that already
gives replay and memoization, seen from a new angle: independent inputs ⟹ independent outputs.
The dataflow *is* the isolation. **We must not build a correlation mechanism to enforce what
purity already enforces** — that would be an artificial control wrapped around a property the
system already has.

This relocates the token. The token is **not** what keeps requests apart (purity does that). The
token is only a **boundary label**: it survives the round-trip so the *host* knows which open
connection to write the reply back to. Isolation is interior and free; routing is at the edge and
is all the token carries.

---

## 3 · The fork resolved: the token is explicit **data**

Two shapes for where routing identity lives:

- **Implicit** — every `Value` silently carries a token (a field, or an ambient context threaded
  by `eval`). Rejected: it puts routing identity *into the value model*, the exact contamination
  Fork B and A→B spent their care avoiding (`Value::Effect` carries a sink *name*, not a typed
  capability, precisely to keep this layer clean). It also re-introduces the ambient channel that
  §2 says must not exist — an implicit token *is* a hidden path two requests could cross on.
- **Explicit** — the token is an **ordinary value** the user threads from request to response,
  like any data. Chosen. Grounded: the `Effect` payload is `Box<Value>`, so a response carries a
  structured `[token, reply]` with **no `Value` change**; the token flows through `eval` as plain
  data. The engine *carries* it (it's just a value); the user *composes* the routing (wires it
  request→response) — the same "engine carries, user composes" split as idempotency (P2.5.2) and
  effects themselves.

Note the two arguments converge: explicit isn't only cleaner, it's the only shape **consistent
with §2.** An implicit ambient token would be a channel outside the pure data path — the very
thing whose absence makes non-crossing free. Keeping the token as explicit data keeps the
isolation theorem true.

---

## 4 · The shape (request/response on a one-way seam)

`Host::perform` returns `()` — the seam is **one-way** (grounded). So a reply does not return into
the graph; it routes **out** through the host. The server-flavor loop:

```
ingress driver  →  supplies [token, request]   (host mints the token = the open connection's id)
      ↓ (token threaded as ordinary data, alongside the request)
   the graph    →  computes a reply from the request
      ↓
response sink   →  Effect{ "respond", [token, reply] }   (the host reads the token, writes reply to that connection)
```

Both ends reuse what exists: ingress is a **driver** (the `SourcedResolver` already injects
host-supplied values), response is a **sink** (an `Effect` whose payload happens to be a
`[token, reply]` pair). The new surface is small: a request-in primitive (`NetworkIngress`) and a
respond-out primitive (`NetworkEgress`) in `capabilities_of`, and the host reading the token off
the payload. **No new value kind, no new `Host` method, no `eval` change.**

Concurrency is the fan-out we already built: `map` over `[(t1,d1),(t2,d2)]` yields
`[Effect{respond,[t1,r1]}, Effect{respond,[t2,r2]}]`. Each carries its own token because each
flowed down its own pure path — **the demonstration of §2.**

---

## 5 · Scope

**Build (modeled):** the two primitives (request-in driver, respond-out sink) in the capability
table; a demonstration that two concurrent requests (a `map` fan-out) produce two responses each
carrying its **own** token — none crossing — with the host (a recorder) capturing the
`(token, reply)` pairs and asserting they match. The point proven: correlation is the token riding
the pure path, and isolation is purity's, not the engine's.

**Defer:**
- **Real routing** — token → an actual open socket — is a **platform host** (the same seam as real
  `email`/clock). The model captures pairs; the real host writes bytes to a connection.
- **Client-flavor await** — "fire a request, *suspend*, resume the graph when the response
  arrives" — is a **graph state-machine across rounds** (a cell holds "awaiting token T"), which is
  async-adjacent (`P2.4.2`, deferred). The server flavor (reply to caller) needs no suspension and
  is what P2.5.1 delivers.
- **Token minting policy** — uniqueness/opacity of the connection id — is the host's (it mints per
  connection); the graph only carries the value.

**Does not touch:** `Value` (token is data), `eval` (token flows like any value), `hash` (runtime
values never in the preimage), the `Host` trait (`perform` already takes an arbitrary payload).

---

## 6 · The one-line shape

> **Correlation is a boundary label, not an isolation engine.** Purity already keeps concurrent
> requests from crossing (independent pure paths, no shared channel); the token is just explicit
> data that survives the round-trip so the *host* can route the reply to the right connection.
> Build the label and the routing demo; let purity do the isolation it already does.
