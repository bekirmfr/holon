# P4.1 — The authoring canvas: the node/edge ↔ unit/hash seam (L4)

**Status:** design note, pre-code. The first editor *surface* inch.
**Stack (decided):** TypeScript (strict) + React + React Flow (`@xyflow/react`), consuming the
`wasm-pack`-generated bindings of `holon-wasm`. Eval runs live through the `Evaluator` we built in
P4.2b. React Flow is the **view**; the content-addressed model stays the source of truth.

---

## 1. What this inch is

A canvas where a human places units, wires their ports (type-checked at the moment of wiring), and
watches the graph evaluate live. Nothing more: not encapsulation-into-a-published-unit (P4.3), not
the registry client (P4.5), not canonical-order-for-cross-author-sharing (deferred — see §7).

## 2. The one hard thing: two models meet at this seam

| | **Editor model** (mutable, per-session) | **Core model** (frozen, identity) |
|---|---|---|
| a node | `{ localId, x, y, hash, openParamValues }` | a slot in `children: Vec<Hash>` |
| a wire | `{ fromNode, fromPort, toNode, toPort }` (local ids) | `Edge { from_child, from_port, to_child, to_port }` (indices) |
| the box | nodes + wires + **layout** | `UnitBody::Composite { children, edges }` + derived interface |
| carries | positions, selection, drag state | only what `encode_preimage` hashes |

The seam is a **deterministic projection** editor → core (to hash and to evaluate) and an inverse
core → editor (to load a unit back onto the canvas). Getting this projection right is the entire
content of the inch, because a wrong projection is how the library's convenience model quietly
becomes the source of truth and smuggles our guarantees away.

## 3. The mapping, precisely (grounded in the real types)

From `hash.rs`: `Unit { body, params: Vec<Param>, inputs: Vec<Port>, output: Option<Type> }`,
`Port { name, ty: Type }`, `Edge { from_child, from_port, to_child, to_port: u32 }`,
`UnitBody::Composite { children: Vec<Hash>, edges }`, `BOUNDARY = u32::MAX`.

- **A canvas node ↔ a child** (a `Hash`). The node *holds a hash*; it never inlines the child's
  body. That is composition by reference (I3) made visible — a node is a citation, not a copy.
- **A node's input handles ↔ that unit's `inputs: Vec<Port>`** (named + typed); **its output handle
  ↔ `output: Option<Type>`.** React Flow handle ids = port indices, so the mapping to `from_port` /
  `to_port` is direct.
- **A wire ↔ an `Edge`.** `from_child` / `to_child` are **indices into `children`**; the composite's
  own interface is index `BOUNDARY` (its promoted inputs feed children; one child's output flows to
  the boundary output).
- **`position` (x, y) and `localId` are VIEW STATE ONLY.** They never enter `encode_preimage`, so
  they never enter the hash (I5 holds). Two people who wire the same units the same way produce the
  same bytes regardless of where they dragged the boxes — *modulo child order*, the one real caveat
  in §7.

## 4. Wire-time type check (I1, fail closed)

When the user drags a wire from output port `P` of node A to input port `Q` of node B, allow the
connection **iff `P.ty == Q.ty` OR either side is `Type::Any`**. `Any` is the deliberate escape
hatch for the polymorphic units (`select`, `get`, `store`, `map`) — there is no unification type
checker, by design, so `Any` is how those wire to anything. Otherwise **reject the wire** — a
type-mismatched graph never comes into existence on the canvas. This is interface parity (I1)
enforced at *authoring* time, not discovered at eval time. `Type::Effect` matches only itself (or
`Any`): an effect request can flow to a boundary output or into `map`, but never back into a sink's
payload slot — effects flow down and out, never back in.

React Flow gives us exactly the hook for this: `isValidConnection`. The check is a pure function of
the two ports' types, read from the units' interfaces — no special machinery, just the parity rule
the core already lives by, applied one wire earlier.

## 5. Live eval — through the **one** evaluator, never a second

**Correctness baseline (what P4.1 ships):** project the canvas to a `Composite`, insert each
*distinct* child unit into the `Evaluator` once, and **evaluate once** through it. That result is, by
construction, the single evaluator's answer — the same `holon_core::eval` the native host and the
marketplace run, compiled to wasm and proven bit-identical in P4.2b. There is no second evaluator.

- **Interface for eval:** use `default_spec` (the core's canonical proposal: promote every unbound
  inner input in `(child, port)` order, expose the unique free output) to derive which ports are the
  composite's inputs and which child is its output. A scratch graph that bottoms out in
  `const`/source nodes has *no* open inputs, so it evaluates with `[]`.
- **Per-node intermediate values** — showing the current value *at every node*, which is the soul of
  a live node editor — is a **separate display layer**, not the correctness baseline. The honest risk
  is that an editor-side topological threading of values silently diverges from the single
  whole-graph eval (that *would* be a second evaluator creeping in). Two acceptable ways to get it
  honestly: (a) a future **traced eval** in core that returns the value at each child index (one
  evaluator, intermediate values surfaced — a small core inch), or (b) an editor topo-layer that we
  **test for agreement** against the single eval (same parity discipline as native↔wasm). KISS lean:
  **ship the whole-graph result first; add per-node values as a tested layer or a later inch.** Do
  not hand-roll an untested second evaluator for the sake of pretty intermediate values.

## 6. Align to the existing seam — do not invent a canonicalizer

The core **does not** canonicalize child order: `encode_preimage` preserves the given order and only
normalizes edge order, with the explicit contract that a deterministic child order is frozen by the
**encapsulation operation** — `derive_and_freeze(children, inner_edges, spec, resolver)`, with
`default_spec` the canonical interface proposal. The editor's projection therefore **drives that
operation** to mint a unit; it must not grow a parallel ordering / interface-derivation path. This is
the natural-boundary rule: the system already has the seam for "freeze a self-contained selection
into a hashed unit," and the canvas is just the thing that *gathers the selection and calls it*.

## 7. The honest caveat: child order is identity, and the canvas can leak placement into it

`order_is_identity` (a real test): two composites with the *same wiring* but a different **child
order** are **different units** with different hashes. The moat — *same hand-authored computation ⟹
same hash ⟹ cross-author cache hit* — therefore requires that the *same visual graph* yields the
*same child order regardless of the order nodes were placed.* The core does not provide this; it
freezes whatever order the caller hands it.

Two honest consequences, and the scoping that follows:

- **For P4.1 (live eval, single session):** eval is correct under *any* consistent child order.
  Placement-order leakage does **not** affect this inch's correctness — a session is self-consistent.
  So P4.1 picks a deterministic-within-session order (topological, ties broken by hash then localId)
  and proceeds. Nothing here is load-bearing on canonicality.
- **Where it actually bites:** the **publish / cross-author boundary** (P4.3 encapsulation UX, P4.5
  registry). There, two authors of a structurally identical graph must land on the same hash, which
  needs a **structure-derived canonical order** (canonical labeling). The hard case is
  **duplicate-hash children** — two `add` nodes — whose tiebreak depends on their wiring, i.e. the
  graph-canonicalization problem in miniature.
- **Decision:** **name it now, defer solving it to the publish boundary.** When solved, it belongs in
  the **core/encapsulation layer** (so every front-end — this editor, a future CLI, anything —
  inherits one canonical order), *not* in the editor. Until then, publishing means "this exact
  child ordering," and we are honest that two differently-built equivalents may not yet share a hash.

This is the most important thing the L4 records: the editor must not paper over child-order
canonicality with an ad-hoc fix on the canvas. That would be exactly the "artificial control bolted
on to quiet a symptom" the project forbids — the real boundary is encapsulation/publish, in the core.

## 8. What P4.1 explicitly does NOT do

- Encapsulate a selection into a *published* unit (drive `derive_and_freeze` for sharing) — P4.3.
- Browse / import-as-pin / publish against a registry — P4.5.
- Canonical child-order labeling — deferred to the publish boundary (§7), and it lands in core.
- Treat layout as identity — positions live in session/side-state, never the hash.
- Per-node live intermediate values as an *untested* layer — baseline is whole-graph eval (§5).

## 9. Invariants touched

I1 (wire-time parity check, fail closed), I3 (a node holds a hash — compose by reference, never
inline), I4/I8 (interface derived via `default_spec`, not asserted by the user), I5 (positions and
local ids excluded from the preimage, so identity is content only), I9 (a placed composite stays
inspectable — you can descend into it; that descent UI is P4.4 but the model already supports it).

## 10. Risks & mitigations

- *Per-node display diverging from the single evaluator* → ship whole-graph eval first; add per-node
  values only as a traced-core result or an agreement-tested layer.
- *Placement leaking into identity at publish* → deferred canonical order in core (§7); until then,
  publish is explicitly "this ordering," stated honestly to the user.
- *React Flow's `{nodes, edges}` state becoming the source of truth* → the core projection is
  authoritative; React Flow state is derived/view, rebuilt from the model, never the other way.
- *Re-implementing topo/threading in TS* → don't; route every computation through `Evaluator`, which
  is the one core eval compiled to wasm.

Stand up the `editor/` Vite + React + TS app in the monorepo, add `@xyflow/react`, wire the
