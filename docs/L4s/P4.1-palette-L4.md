# The palette + custom nodes (L4)

**Status:** first inch of the P4.1 authoring canvas, and the first *visual* surface. Stands on the
`primitive_catalog()` bridge. Browser-confirmed, not test-confirmed (see §6).

---

## 1. Scope — exactly this inch

Place real primitive nodes on the canvas, derived from core's catalog:

- A **palette** listing every genesis primitive, built from `primitive_catalog()` — not a hand-written
  TS list.
- A **custom node** that renders a primitive as a typed block: its name, one input handle per input
  port, one output handle, each **colored by its wire type**.
- **Drag a primitive from the palette onto the canvas** to place an instance; React Flow handles
  move/pan/zoom.

**Not this inch** (each its own next inch): wiring + the `isValidConnection` type check; projecting
the canvas to a composite and evaluating; editing a node's params. Nodes this inch are placed and
inspectable but not yet connected.

## 2. The load-bearing rule: ports come from the catalog, never hand-placed (I1)

A canvas node's handles are rendered **from the interface `primitive_catalog()` returned** — the same
`Unit` core would build for that primitive. `node.data` carries that interface (`name`, `inputs`,
`output`, `params`); `PrimitiveNode` renders one handle per `inputs[i]` and one for `output`. The
editor never asserts "add has two number ports"; it reads them from core. This is I1 made structural:
the only source of a node's shape is the catalog, so the canvas and core cannot disagree about what a
primitive is. (It's why the bridge inch came first.)

## 3. Canvas state model

A canvas node is a *placed instance* of a primitive:

```
{ id: localId, type: "primitive", position: {x,y},
  data: { name, inputs: WPort[], output: WType|null, params: WParam[] } }
```

`id` and `position` are **view-only** — they're how the editor tracks and lays out a node, and they
are excluded from identity (I5), exactly as the authoring-canvas L4 said. They never enter a
preimage. When projection lands (a later inch), the composite is built from the *interfaces and
wiring*, and `position`/`localId` are dropped on the floor. Handle ids are the **port names** (input)
and `"out"` (output) — stable references the wiring inch will turn into `Edge`s by index.

## 4. Design direction (frontend-design plan)

**Subject.** A schematic editor for composing *pure, content-addressed* computation — builders wiring
typed blocks. Its world is types, ports, and hashes, not marketing.

**Signature — type as color.** The one bold, grounded choice: every port is a dot **colored by its
wire type**, and the editor's whole palette is derived *from the type system*, not decoration. Six
types, six hues. When wiring lands next inch, a legal connection is two ports of the same hue (or
`Any`, the neutral) — the type check made visible before it's even enforced. Boldness spent here;
everything else stays quiet.

**Tokens.**
- Color (blueprint-ink substrate, near-monochrome so the type hues carry all the color):
  `--bg #0b1220` · `--panel #131d31` · `--line #273a59` (hairline grid) · `--ink #e8eef7` ·
  `--ink-dim #7e8ea8` · `--accent #6fd3e0` (chrome only).
  Type hues: Number `#f2b441` · Boolean `#46c8d8` · Text `#5fd38a` · List `#b48cf0` ·
  Effect `#ff6f6f` · Any `#8295b0`.
- Type: **IBM Plex Mono** for everything — an instrument that edits code-like atoms should speak in
  mono; hierarchy comes from weight (400/500/600) and size, not a second family. Disciplined, not a
  neutral delivery vehicle.
- Layout: thin header (identity + leaf count) · fixed-width palette left · canvas fills the rest.

```
┌───────────────────────────────────────────────┐
│ holon · authoring            34 genesis atoms  │
├──────────────┬────────────────────────────────┤
│ PALETTE      │ · · · · · · · · · · · · · · · · │  blueprint grid
│ const        │ · · · ┌──────────┐ · · · · · · ·│
│ add          │ · · · │ add      │ · · · · · · ·│  node: name +
│ multiply     │ · ·  a○│         │○ · · · · · · │  type-colored
│ …            │ · ·  b○│         │  · · · · · · │  ports
│ egress       │ · · · └──────────┘ · · · · · · ·│
└──────────────┴────────────────────────────────┘
```

**Critique vs. the AI defaults.** Not cream/serif/terracotta; not a single-acid-accent on near-black
(the hues are a *six-type system*, each meaningful, not one decorative accent); not broadsheet rules.
Blueprint-ink + mono + color-derived-from-types is grounded in "a schematic of typed computation."
The risk — letting the *type system* supply the entire palette and keeping the chrome near-monochrome
— is justified because in Holon the type **is** the structure being composed.

## 5. Palette order

Rendered in `primitive_catalog()` order, which is §13a manifest order (pure core → text → list →
drivers → state → sink). The clustering is already meaningful; no TS-side category map is invented
(that would be a second assertion that could drift). A flat, ordered list — honest and simple.

## 6. What this inch proves, honestly

The palette deriving from core (no hand-written list) and the node↔interface mapping are the real
content; their correctness is **visual** — does a dragged `add` show two amber (`Number`) inputs and
one amber output; does `select` show a cyan `Boolean` then two slate `Any` inputs. There is no React
test runner in `editor/`, so this inch is confirmed in the browser, not by a count. The *provable*
part — projecting the canvas to a composite and evaluating it through the one `Evaluator` — returns in
a later inch, on the path the heartbeat already exercised. Stated plainly so the green/▢ status is
honest.

## 7. Run

Rebuild the wasm so the bridge's `primitive_catalog` is in the generated module, then dev:

```
cd crates/holon-wasm && wasm-pack build --target web --out-dir ../../editor/wasm
cd ../../editor && npm run dev
```

(No new npm deps — still React + `@xyflow/react`.)

## 8. Invariants

I1 — the node's ports are read from core's catalog, never hand-asserted. I5 — `position`/`localId` are
view-only, never in identity. I8 — the palette is *derived*, not declared.
