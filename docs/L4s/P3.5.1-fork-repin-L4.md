# P3.5.1 — Fork / re-pin (the sanctioned creation of a new identity) · L4 design note

## What this inch is

Every operation so far **preserves** identity: hashing, pinning, publishing, inspecting,
memoizing all take a unit's hash as fixed and trustworthy. Fork is the one operation that
deliberately **creates a new identity** — the marketplace's mechanism for derivation and
improvement. You take a published unit, swap one of its referenced parts for a different one,
and get a genuinely new unit with a new hash that anyone can pin, inspect, and memoize exactly
like any other.

"Re-pin" names the mechanic: a composite pins its children *by hash* (I3, I6). To change a
child is to pin a *different* hash there — which changes the parent's preimage, which changes
the parent's hash, which changes how *its* parents pin it, and so on up to the root. Fork is
that re-pin, propagated correctly.

## The core mechanic: path-copying with structural sharing

Changing a deep node re-hashes **only the path from that node to the root**; every subtree off
that path keeps its original hash and is shared by reference. This is exactly how persistent
immutable trees (and Unison, and git) work, and it falls straight out of content-addressing.

```
        R ─► [A, B]                 R'─► [A', B]          B shared (unchanged)
        A ─► [C, D]      replace    A'─► [C, D']          C shared (unchanged)
                          D→D'                            D' supplied by the forker
   new units minted: A', R'  (the re-pinned spine); new root = R'
```

`B` and `C` never change, so their hashes — and everything they transitively pin — are reused
untouched. Only `A` and `R` (the ancestors of `D`) are re-minted. This is the content-addressing
payoff: a one-node change costs one path, not a deep copy.

## The pure transform (core)

```
pub struct Refork {
    pub new_root: Hash,                  // key of the new root within `minted`
    pub minted: BTreeMap<Hash, Unit>,    // the re-pinned spine (new units to store)
}

/// Re-pin every reference to `target` → `replacement` in the DAG below `root`, path-copying
/// the affected ancestors. `None` if `target` is not in `root`'s closure (nothing to fork).
pub fn refork(
    root: &Unit, target: &Hash, replacement: &Hash, resolver: &impl Resolver,
) -> Option<Refork>;
```

Recursion (returns `Some(new_hash)` if the subtree changed, `None` if untouched):

```
refork_node(unit) -> Option<Hash>:
    changed = false
    new_refs = for each reference r of `unit` (children ∪ the `fn` param, per child_refs):
        if r == target:                       changed = true; replacement
        else if let Some(u) = resolve(r):
            match refork_node(u):
                Some(h2) =>                    changed = true; h2
                None     =>                    r            # subtree unchanged → shared
        else:                                  r            # unresolvable → treat as unchanged
    if changed:
        new_unit = `unit` with its references rewritten to new_refs
        h = hash_unit(new_unit); minted.insert(h, new_unit); Some(h)
    else:
        None
```

Re-pinning is **uniform with `child_refs`** — the same references inspection *reads*, fork
*rewrites*: a child is a hash swap in `children`; a `fn` param becomes
`Param::frozen("fn", to_hex(replacement))` (the inverse of the `parse_hash` eval uses to read
it). One definition of "what a unit references," now readable and rewritable.

The transform is **pure**: given a resolver it mints new units and returns them; it stores
nothing. (FCIS, same split as memo: pure derivation in core, stateful storage in host.)

## Provenance: the forked unit carries none

Content-addressing makes the forked unit **genuinely independent** — `R'` is just a unit, with
no embedded "I am a fork of `R`" pointer. Embedding one would be self-defeating: it would change
`R'`'s hash, and there's no stable thing to point *at* anyway. So **provenance lives outside the
unit, if it lives at all** — a registry annotation (`R'` derives-from `R`), which is a separate,
deferred concern (the marketplace can also surface relatedness *structurally*, since `R'` and `R`
share most of their closure by hash). For P3.5.1, fork produces a clean new identity and records
no link. This is a feature: a forked unit is trustless on its own terms, audited by its own
closure, beholden to nothing.

## Forks (surfaced; recommendations are not yet decisions)

- **F1 — replace-all vs replace-at-one-path. → replace-all (by hash).** `target` is one
  identity (hash = identity); wherever it appears it is the *same* unit, so "improve it" means
  everywhere it's pinned. Path-addressed surgical replacement is more machinery and less aligned
  with content-addressing. Replace-all is the natural semantics.
- **F2 — transitive path-copy vs single-level re-pin. → transitive.** Handles any-depth change
  with structural sharing; single-level (swap a direct child only) is just its shallow case and
  would force the caller to hand-propagate. Transitive is the real operation.
- **F3 — provenance: embed / external / none. → none in the unit** (reasoned above); external
  annotation deferred.
- **F4 — replacement passed as Hash vs Unit. → Hash.** `refork` only rewrites *references*; the
  replacement unit's own storage is the caller's concern (they built it; they store it). Clean
  separation, and lets you re-pin to an already-published hash without re-handing the unit.
- **F5 — `target` not in closure: `None` vs error. → `None`.** It's a valid query that found
  nothing to change, not a failure; the caller decides what to do.
- **F6 — unresolvable child mid-walk: lenient (treat as unchanged) vs error. → lenient, with a
  note.** Fork is meant for *published* roots, whose closure is complete by construction (the
  registry guarantees it, P3.1.1), so this never arises in the intended path. Lenient keeps the
  transform total; the honest caveat is that re-pinning a target hidden inside an *unresolvable*
  subtree of an incomplete unit would be missed.

Note: fork is structural (re-pinning *references*). Changing a frozen **param value** or
opening a param is a different, existing mechanism (`promote`/`encapsulate`, P1) and is out of
scope here.

## Host assembly (refork + existing pieces)

The marketplace fork is mostly **assembly of pieces that already exist**:
```
Registry::fork(root_hash, target, replacement_unit) -> Result<Hash, …>:
    1. resolve `root` from the store; store `replacement_unit` → replacement_hash
    2. materialize root's closure into a resolver (walk child_refs via store.get)   ‹glue›
    3. refork(root, target, replacement_hash, resolver) → Refork { new_root, minted }
    4. store every unit in `minted`
    5. publish(new_root)  — its closure is complete by construction:
         minted spine ∪ shared-unchanged (already stored) ∪ replacement (stored in 1)
    6. return new_root
```
Step 5 reuses `Registry::publish` and its closure check verbatim, so a fork that re-pins to a
missing replacement is caught by the *existing* `DanglingReference` gate — fork inherits the
publish invariant for free.

The one piece of glue is step 2: the store yields owned units (`get`), `refork` wants a
`Resolver` (`&Unit`), so the host materializes the bounded closure into a `MapResolver` first.
(This store↔resolver duality has now recurred in registry, inspection, and fork — a `Store`→
`Resolver` adapter is a reasonable future tidy, noted, not built here.)

**Build scope question to settle:** deliver the pure `refork` (core) this inch with thorough
`MapResolver` tests, and either (a) include the thin `Registry::fork` assembly now, or (b) land
`refork` alone and add the host assembly as a short follow-on. Recommendation: include the host
assembly if the closure-materialization glue stays small; otherwise split. The *design-heavy*
part is entirely in `refork`.

## Tests (what green must prove — core `refork`)

1. **re-pin a direct child** — `root → [A, B]`, replace `A` → `A2` ⇒ new root pins `[A2, B]`;
   `B` shared.
2. **re-pin deep, with sharing** — `root → [A, B]`, `A → [C, D]`, replace `D` → `D2` ⇒ `A` and
   `root` re-minted, `B` and `C` hashes unchanged (assert they appear untouched).
3. **re-pin a `fn` param** — a `map`/`fold` whose `fn` is `target` ⇒ new unit's `fn` param is
   `to_hex(replacement)` (and `child_refs` of the result points at `replacement`).
4. **replace-all** — `target` referenced in two places ⇒ both re-pinned in one fork.
5. **target not in closure ⇒ `None`** — nothing to fork.
6. **minted set is exactly the spine** — off-path subtrees are not in `minted` (sharing, not
   copying).
7. *(if host assembly included)* **forked root re-publishes** — `Registry::fork` then the new
   root is published and its closure verifies; re-pinning to an unstored replacement is refused
   by the existing dangling gate.

Expected: core `refork` (~6 tests); host `fork` (~1–2 tests) if included.

## Why this is the right inch

Fork is the marketplace's generative act — without it the registry is a read-only museum. And
it's almost entirely *composition* of what's built: `child_refs` (one reference definition),
`hash_unit` (re-mint), the store, and `publish` (whose closure gate fork inherits). The only new
logic is the path-copying transform, and the only real decisions are replace-all, transitivity,
and provenance-is-external — each of which falls the way content-addressing already points.
