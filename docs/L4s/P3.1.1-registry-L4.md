# P3.1.1 — The registry (the first permanent publish) · L4 design note

## What this inch is

The **publish boundary**: where a unit stops being a private working artifact and becomes a
**published** one — a hash others may permanently depend on. This is the first time a hash
becomes a public commitment, so it is the moment the marketplace's trust model is first
anchored. It is consequential precisely because it is *permanent*: a consumer who pins a
published hash expects it to resolve, forever, to the same closed unit.

Everything the registry will eventually grow — names, discovery, reputation, networking —
is a refinement layered **on top of** this boundary. The boundary itself has exactly one
load-bearing job, below.

## The load-bearing invariant: closure-completeness (I6 at the publish boundary)

**You cannot publish a unit whose transitive closure is not fully present.** A composite
references its children *by hash* (I3); a higher-order unit (`map`/`fold`) references its
`fn` *by hash* in a param (I6). If any of those referenced hashes does not resolve in the
store, the published unit is **dangling** — a consumer would fetch it and be unable to
evaluate or even inspect it. Publishing a dangling unit would poison the trust root the
instant it is committed.

So `publish` **fails closed** on any dangling reference. The closure walk is the same one
`simulate::collect_mocks` and `kind::capabilities` already use — follow
`UnitBody::Composite.children` *and* every hash-valued param — and it terminates for free
because content-addressing forbids a cycle. Each `store.get` along the walk *also*
re-verifies integrity (the store's verify-on-read, P3.8.1), so closure verification reuses
that check for free: a referenced hash that resolves is, by construction, the right bytes.

This is the whole point of the inch. Names and persistence are conveniences; **closure
verification is the commitment's meaning.**

## Recommended shape (minimal, KISS)

Lives in **`holon-host`** (it drives a `Store`, which is I/O). The closure-walk logic is new
but mirrors `collect_mocks` minus the mock-building.

```
pub enum PublishError {
    Store(StoreError),
    DanglingReference(Hash),   // a child / param hash not present in the store
}

pub struct Registry<S: Store> {
    store: S,
    published: BTreeSet<Hash>, // append-only record of explicitly published roots
}

impl<S: Store> Registry<S> {
    pub fn publish(&mut self, root: &Unit) -> Result<Hash, PublishError> {
        // 1. verify the closure is complete *before* committing anything
        verify_closure(root, &self.store)?;        // walk children + hash-valued params
        // 2. commit: store the root, record it as published
        let h = self.store.put(root).map_err(PublishError::Store)?;
        self.published.insert(h);
        Ok(h)
    }
    pub fn is_published(&self, h: &Hash) -> bool { self.published.contains(h) }
    pub fn published(&self) -> impl Iterator<Item = &Hash> { self.published.iter() }
}
```

`verify_closure(root, store)` walks `root`'s children and hash-valued params; for each, a
`store.get(h)?` of `None` ⇒ `DanglingReference(h)`, of `Some(child)` ⇒ recurse. (The root
itself is held as `&Unit`, so we walk *its* references directly rather than fetching it.)
Verify-first-then-commit means a failed publish leaves nothing extra in the published set.

## Forks (surfaced; recommendations are not yet decisions)

**F1 — name, or hash only? → recommend hash-only.** Hash *is* identity (the thesis). A
naming layer (`"double" → hash`) is contentious (two authors, two units, one name), social,
and properly a *discovery* concern — likely part of the networked tier, not the publish
primitive. The first publish commits a hash and its verified closure; discovery-by-name is a
later refinement that never weakens this boundary.

**F2 — catalog persistence: in-memory now, or persist the record? → recommend in-memory for
this inch.** The *units* are already persisted (the store); only the *published-set record*
is in-memory here. The consequential part — closure verification — is fully realized
in-memory. Persisting the catalog (a small newline-of-hex file, or a reserved store entry)
is mechanical plumbing best taken as its own short follow-on, so "permanent across restarts"
lands in a focused inch rather than riding on this one. Flag honestly: until then,
"permanent" means *within a session*; the boundary and its invariant are what we're
establishing now.

**F3 — re-publish: idempotent.** Publishing an already-published hash is a no-op that
returns the same hash (the set is append-only; content-addressing makes this trivially
safe). No error, no fork really — just stated so it's not a surprise.

**F4 — does publish mark the whole closure published, or just the root? → recommend just the
root.** The published-set records what the author *chose* to publish (the roots — the
discoverable entries). The closure is *verified-present* and therefore available to any
consumer via the store, but a dependency is not itself a discoverable published entry unless
separately published. A consumer always resolves the full closure from the store regardless
of the dependencies' published-status, so nothing breaks; this just keeps "published" meaning
"an entry someone chose to offer," not "every leaf underneath it."

## What this inch deliberately does NOT do

- No names / no discovery index (F1 — later, likely networked tier).
- No catalog persistence across restarts (F2 — next short inch).
- No networking / no shared registry (the whole networked tier stays deferred).
- No reputation, identity, or signatures (P3.4/P3.7 — deferred).

## Tests (what green must prove)

1. **publish a leaf** → `Ok(h)`; `is_published(h)`; `store.get(h)` is `Some`.
2. **publish a composite whose children are stored** → `Ok(root)`; `is_published(root)`.
3. **dangling child ⇒ fail closed** — build a composite referencing a child hash that was
   never stored; `publish` ⇒ `Err(DanglingReference(child))`. *(The invariant.)*
4. **dangling hash-valued param ⇒ fail closed** — a `map`/`fold` whose `fn` hash is absent ⇒
   `Err(DanglingReference(fn))`. *(Proves the walk follows params, not just children — the
   I6 subtlety that a naive children-only walk would miss.)*
5. **re-publish is idempotent** — publishing the same unit twice ⇒ same hash, still one
   entry, no error.

Expected: +1 test module in `holon-host` (≈5 tests). No `holon-core` change — the registry is
pure host orchestration over the existing `Store` and the existing closure shape.

## Why this is the right first P3 inch

P3 is "mostly exposure, not invention": content-addressing, transitive pinning (I6), purity
classification, full inspectability (I9), and the store (P3.8.1) are all already built and
green. The registry doesn't invent a trust mechanism — it *enforces, at the publish moment*,
the closure property the rest of the system already guarantees structurally. It is the
smallest thing that makes "a hash is now public" mean something verifiable.
