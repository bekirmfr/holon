# L4 — P3.4.1: reputation-by-adoption

**The navigation layer.** The marketplace will hold thousands of published units. A consumer can
*inspect* any one (I9) and *verify* any result (P3.3.2) — but not inspect everything. They need a
**discovery signal**: which units are worth attention, which are trusted building blocks? P3.4.1 is
that signal, derived from the one thing that can't be faked — the published content graph itself.

Before the design, a correction I owe.

---

## Correction to my own earlier framing

I previously described P3.4.1 as "how trust gets earned so a consumer can use a `get` result rather
than always paying for `get_verified`" — i.e. **result-trust** (skip compute on a stranger's word).
On reflection that was wrong about what's buildable here, for a precise reason:

A cache *result* is **objectively verifiable** — re-execution settles it, and because eval is
deterministic, *every honest party who computes `(U, I)` gets the same `V`*. So a wrong `V'` can
never accumulate honest endorsements; the correct `V` is the unique attractor. That's lovely, but to
*count* endorsements you must count **distinct parties** — which is Sybil-resistance, which needs
**identity** (P3.7.1). Without identity, "50 parties verified this" is forgeable by one party
claiming 50. So result-trust-by-adoption is genuinely **blocked on identity**, and belongs after
P3.7.1 (or behind staking).

What *is* buildable now, identity-free, is reputation for **units** — and it turns out to be the more
useful half anyway, because a unit's quality is *not* objectively verifiable (you can't re-run
`quicksort` to learn whether it's *good*), so an aggregate adoption signal tells you something you
genuinely can't derive yourself.

---

## The idea: adoption = inbound citations in the published DAG

Define a unit's adoption as **how many published units directly reference it** (`U ∈ child_refs(X)`)
across the entire published universe (every unit in any published root's closure). This is a
content-graph fact — the citation count of `U`.

Why this is a real trust signal *here* specifically, not just popularity: in a content-addressed
world, **adopting `U` means pinning its exact hash** — committing to its frozen, fully-inspected
behavior *forever* (I5 + I9). It can never change under you. So an adoption is a far stronger
signal than a "star" in a mutable system: it's evidence that a party inspected that exact behavior
and built on it, knowing it's immutable. A widely-cited hash is one many parties independently
vetted and froze.

---

## The load-bearing property: derived, not asserted (I8)

Adoption is **never a stored counter** (a "like" button — forgeable, drift-prone, a number someone
can edit). It is **recomputed from the actual published DAG** on every query. So it cannot be
inflated *except by publishing real referring units* — which are themselves content-addressed and
inspectable. The reputation signal is exactly as trustworthy as the content graph it's read from.

This is the thesis extending one more step: content-addressing made memoization *trustless*
(P3.3.2); now it makes reputation *unfakeable-by-assertion*. Both are the same move — **you can't
lie because the truth is in the content, not in a claim beside it.**

---

## Proposed surface

### Core — `inspect.rs` (the inspection family; reuses `child_refs`)

```rust
/// Inbound direct-citation counts over a corpus: for each referenced hash, how many *distinct*
/// units in the corpus reference it. Pure — a function of the content graph. (A unit that cites
/// `U` twice counts once: the signal is "distinct adopters", not raw edges.)
pub fn adoption_counts<'a>(corpus: impl IntoIterator<Item = &'a Unit>) -> BTreeMap<Hash, usize>;
```

### Host — `Registry`

```rust
/// Adoption over the *published universe* (every unit in any published root's closure), derived
/// fresh from the store — never a stored tally. `StoreError` if the walk hits a read error.
pub fn adoption(&self) -> Result<BTreeMap<Hash, usize>, StoreError>;
```

Host gathers the corpus by walking each published root's closure from the store (the `verify_closure`
pattern, collecting instead of checking), then calls the pure core tally. FCIS split as ever:
pure counting in core, the store-walk in host.

## Forks & resolutions

1. **Subject / honest scope** → **units** (structural, identity-free, buildable now), *not*
   result-trust (objectively verifiable, needs identity to count distinct endorsers — deferred to
   P3.7.1). *This is the framing correction above.*
2. **Signal source** → **structural citation** (DAG inbound refs). Not attested (needs identity),
   not economic (needs stake).
3. **Derived vs asserted** → **derived from the DAG** (I8), never a stored counter. The load-bearing
   choice — reputation you can't fake by editing a number.
4. **Direct vs transitive** → **direct citation** within the published universe (so deep library
   units *are* counted, by their direct citers). Transitive-reach and recursive/eigenvector
   weighting deferred.
5. **Distinct vs raw** → distinct referrers (dedup each unit's `child_refs`): one flow building on
   `U` counts once even if it uses `U` in two slots.
6. **FCIS placement** → core `adoption_counts` (pure), host `Registry::adoption` (store-walk).

---

## Honest limits (named, not hidden)

- **Not Sybil-resistant.** An attacker can publish junk units citing `U` to inflate it. The junk is
  cheap to make but *inspectable*. The fix is **recursive weighting** (a citation from a
  high-adoption unit counts more; junk citers have ≈0 adoption ⇒ contribute ≈0) — i.e. PageRank over
  the DAG. That is a global eigenvector computation, heavier, with global iteration; **deferred**
  with a trigger: when corpus size makes flat counts noisy, or Sybil inflation is actually observed.
- **Not result-trust.** Skipping compute on a stranger's word needs identity (P3.7.1) or stake. The
  determinism-attractor insight (honest parties all land on the same `V`) is what will make it work
  *once distinct endorsers can be counted* — so this inch lays the conceptual groundwork, but the
  mechanism waits.

---

## THE TWO DECISIONS REQUESTED

**(A) Scope** — confirm P3.4.1 = **unit adoption by citation** (identity-free, derived, advisory),
and that **result-trust is re-scoped onto P3.7.1**, not delivered here. (My recommendation: yes.)

**(B) Ordering** — proceed **adoption-first** (build this now; identity later *hardens* it with
Sybil-resistance and *extends* it to result-trust), or do **P3.7.1 identity first** so reputation is
Sybil-resistant from the start? My recommendation: **adoption-first** — the identity-free structural
signal is immediately useful for discovery and is the foundation identity refines, and building it
now surfaces exactly what identity must later support. But identity-first is defensible if you'd
rather not ship a knowingly-Sybil-weak v1 even as a labeled stepping stone.

---

## Test plan (core ~4, host ~3 ⇒ ~190 total)

Core: empty corpus → empty; one referrer → count 1; N distinct referrers → N; double-cite → counts
once (dedup); a `fn`-param reference is counted (adoption sees combinators too, via `child_refs`).
Host: published root → its child has adoption 1; two roots citing one child → 2; a deep library unit
cited by an intermediate (not a root) → counted (corpus = closures, not just roots).
