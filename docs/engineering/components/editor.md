# The editor

The web editor: where a person draws or writes a flow, deploys it after seeing what it may do, and
reads its runs back node by node. Written for someone who will change it.

## 1. What it is

`editor/` is a React 18 and TypeScript app built with Vite, drawing the canvas with React Flow
(`@xyflow/react`) and the text with CodeMirror 6. It runs the same core and the same language as
the server, compiled to wasm: `editor/wasm`, generated by `wasm-pack` from `crates/holon-wasm`
(which wraps `holon-core` and `holon-author`), never edited by hand and not in git. It talks to a
Holon server over its REST API (`src/server.ts`), and the server serves it at `/`.

A second editor, `holon editor`, runs in a terminal (`crates/holon/src/workbench`); §2 says how
the two relate. The language and compiler it calls are [holon-author](holon-author.md)'s.

## 2. How it works

### The parts of `editor/src`

- **The canvas.** `App.tsx` holds the canvas, the palette (`Palette.tsx`: saved flows, marketplace
  listings, and the templates then every genesis primitive by catalog category) and its panels
  (`CanvasPanels.tsx`). A node is `PrimitiveNode.tsx`, its handles drawn only from the interface
  the catalog gave, each coloured by its wire type (`theme.ts`). `canvasOps.ts` projects, groups
  and places; `composites.ts` and `CompositeOverlay.tsx` open a holon on a canvas of its own and
  freeze it back. `history.ts` is undo: a snapshot 400 ms after edits settle.
- **The text pane.** `TextPane.tsx`, `useTextPane.ts`, `textSync.ts`, `textLink.ts`, over
  `holonText.ts` (below).
- **Tabs and pages.** `tabs.ts` and `useTabs.ts` keep one tab per open flow, each in edit or view
  mode. `Pages.tsx`'s `AppPage` is `canvas`, `flows`, `deployed`, `admin`, `home`, `welcome` or
  `docs`; the canvas is never unmounted, the others are overlays on it. `FlowsPage` lists saved
  flows and the samples; `DeployedPage` lists deployments as `DeploymentCard.tsx`s (status, run,
  pause, stop, its run sessions, delete once stopped). `AdminPage.tsx` has three tabs (`people`,
  `resources`, `permissions`), for admins. `HomePage.tsx` and `WelcomePage.tsx` keep their layout
  with the account (`home.ts`, the server's `/auth/prefs`); `ManualPage.tsx` shows `docs/manual`,
  read at build time (`manual.ts`), and is loaded lazily.
- **Deploying.** `DeployBar.tsx` and `useDeployFlow.ts`: the flow's unit (`flowUnitHash`), its
  closure staged (`stageClosure`, each unit by `POST /unit`), `previewDeploy`
  (`POST /deploy/preview`) for what it may touch, the consent dialog, then `deployUnit`. `touches.ts`, `Manifest.tsx` and
  `DryRun.tsx` say what a deploy or a restore would change.
- **View mode.** `useViewMode.tsx`, `ViewPanes.tsx`, `HistoryPane.tsx`, `CellHistory.tsx`: a
  deployed flow, read only, with its runs. `replay.ts` replays a logged run on the canvas node by
  node from what the log recorded (the request, the state read, the clock, random numbers,
  ingress), and the editor says whether that reproduced the run; which nodes ran follows core's
  choice rule (`choiceNext`). `timeline.ts` merges runs, versions and events as `holon history`
  does.
- **The API client.** `server.ts`, typed against the server's JSON. Its `BASE` is
  `VITE_HOLON_SERVER` when set; else, built, the origin it was served from; in development
  `http://127.0.0.1:7420`. The session is kept in `localStorage` under `holon.session`.
  `AuthGate.tsx` and `signin.ts` sign in (a password, or the server's identity provider).
- **`storage.ts`** is not browser storage: it is how the admin page words the server's own sweeps
  and holdings (the server's `storage.rs`).

### The wasm bridge

`holon.ts` is the typed facade: `ensureReady` loads the module once (`init()`), and its types
(`WType`, `WParam`, `WPort`, `WUnit`, `WValue`) mirror holon-wasm's serde types. Through it:

- the catalog (`primitive_catalog`, `primitive_docs`), the wire check (`compatible`), hashing
  (`build_preimage`), and an `Evaluator` that holds units and evaluates, groups, freezes, derives
  servers (`derive_server`, `flow_unit`), says capabilities and prints text (`print_holon`,
  `print_holon_lines`);
- the routes (`derive.ts` → `find_routes`, `canvas_components`) and templates (`templates.ts`);
- the language (`holonText.ts` → `compile_holon`, `holon_mistakes`, `holon_hover`,
  `holon_complete`, `holon_format`, `holon_highlight`, `holon_runnable_by_hand`), positions
  crossing as UTF-16 offsets, converted in the bridge (`Offsets`);
- the samples (`samples.ts` → `samples`, `build_sample`).

It is built with `wasm-pack build crates/holon-wasm --target web --out-dir ../../editor/wasm`
(CI adds `--no-opt`, as releases do). `e2e/server.mjs` rebuilds it when it is older than
`holon-core`, `holon-author`, `holon-module`, `holon-wasm` or `Cargo.lock`.

### The text pane

The pane shows the flow as `fmt` writes it or as it was typed. An edit is compiled after
`PAUSE_MS` (300 ms); compiled, it replaces the canvas's document as one undo step, and
`carryOver` keeps each node it didn't touch where it was, with its id, matching nodes by their
name in the text or where they are written; not compiled, the mistake is marked and the canvas
keeps the last version that compiled. A canvas change prints the text again. The text as typed is
saved as the document's `source`. `textLink.ts`'s `pickAt` and `dimmed` link a cursor to the
innermost node written under it and dim what a run didn't reach; view mode compiles the text it
printed and matches it to the deployed canvas with `syncedFromCanvas`. The pane opens by default
when the window is at least `TEXT_OPEN_WIDTH` (1600 px) wide.

### How the server serves it

`crates/holon/src/editor.rs`: `Source::pick` takes `--editor DIR` (or `HOLON_EDITOR`) when given,
else the editor built into the binary (the `embed-editor` feature, `editor/dist` by `include_dir`,
as releases are built), else none. `serve` answers only a GET (`http.rs` checks) for `/` or a path
whose last segment has a dot, only for files inside the editor; everything else is the API's.
Assets are cached as immutable, the page as `no-cache`. In development, `npm run dev` serves it
from Vite against a server on 7420.

### The terminal editor

`holon editor` (`crates/holon/src/workbench`, ratatui) is the same product in a terminal: the
flows on a server, what waits for a person, a flow's runs and history, and its text in tabs,
checked as it is typed. It shares no code with the web editor but the language: it calls
holon-author natively (`editing::mistakes`, `editing::highlight`, `agent::plan` to deploy,
`agent::text_of` and `agent::run_view` to read a deployment, `graph::graph` for its graph,
`usage::usage` for its inspector, `samples` for its palette), and the server over HTTP
(`client.rs`). It has no canvas: a flow is drawn as rows of statements. Without a server it still
edits, checks and formats files.

## 3. Why it is this way

- **One core, through wasm.** No TypeScript copy of the encoder, the evaluator, the catalog or the
  language: one would be free to drift (LANGUAGE.md §2, P5). The catalog crosses in one call,
  through the converter `load_unit` already used
  ([primitive-catalog bridge L4](../../L4s/primitive-catalog-bridge-L4.md)).
- **TypeScript, typed at the boundary.** The generated `.d.ts` types the bridge as `any`;
  `holon.ts` mirrors the Rust types as discriminated unions, so the compiler checks what crosses.
  `server.ts` does the same for the API.
- **Ports from the catalog, never placed by hand** (invariant I1), and a wire type is a colour
  ([palette L4 §2, §4](../../L4s/P4.1-palette-L4.md)). The wire check is core's `compatible`,
  fail closed ([wiring L4 §1](../../L4s/P4.1-wiring-L4.md)).
- **The editor assembles, the core derives.** The canvas hands core children and edges; core
  decides the boundary and the hash, so moving a node changes no hash and rewiring does
  ([projection L4 §0, §4](../../L4s/P4.1-projection-L4.md)). Positions are view state only
  ([authoring canvas L4 §3](../../L4s/P4.1-authoring-canvas-L4.md)).
- **CodeMirror, not Monaco**: small packages, each taking a function the language already
  answers ([text-pane L4](../../L4s/text-pane-L4.md), decision 1).
- **The last edit wins.** A canvas edit and the same edit typed are one change to the flow, so
  both stay editors and the other follows (decision 7); the pause is for the person, since a flow
  compiles in milliseconds (decision 3).
- **Ranges as UTF-16 offsets; the printer stays line-based.** View mode compiles what it printed
  and matches it, one mapping for both modes
  ([text-graph-link L4](../../L4s/text-graph-link-L4.md), decisions 1 and 2).
- **In-page dialogs** (`Dialog.tsx`): an embedded browser suppresses `window.confirm`, which then
  answers "cancel" at once, so deletes and first saves did nothing there.
- **Served by the server.** One process and one port: on a machine without a screen, start the
  server and open it from any browser (`editor.rs`).
- **End-to-end clicks are dispatched** (`dispatchEvent("click")`): a forced click lands on
  whatever covers the button, and the test waited out its 180 s timeout (`38470d1`). Tests that
  need no browser after deploying moved to `system.e2e.ts`, deployed with `holon deploy`
  (`1e882b4`).

## 4. Reach and limits

- **The bundle carries the js engine**: 6 MB, from 1.9 before
  ([js-node L4 §7](../../L4s/js-node-L4.md)).
- **No declare quick fix.** The web editor's Format adds missing declarations as `fmt` does, but
  it offers no button for them, which `holon lsp` does
  ([declared-names L4 §10](../../L4s/declared-names-L4.md)).
- **The text pane** edits no holon's inner text from its overlay; the cursor inside a holon's
  definition picks nothing (text-graph-link, decision 7); a layout lives only in the editor's
  saved flow, so a `.holon` imported is laid out afresh; no two people on one flow
  ([text-pane L4](../../L4s/text-pane-L4.md)). A canvas edit that reprints drops the text's
  comments; the pane says how many, and undo brings them back.
- **A stale bridge.** `editor/wasm` is built by hand outside CI; one older than its crates lacks
  what they added (a new sample has no card) until rebuilt (`5e6030c`).
- **Components are tested in a browser only.** The unit tests are pure logic against the real
  core; `PrimitiveNode.test.tsx` is the one that renders a component. Everything drawn is held by
  the end-to-end tests.
- **The end-to-end editor is Vite's**, not the built one: `playwright.config.ts` starts
  `npx vite` against the test server. The built and embedded editor is held only by `editor.rs`'s
  tests.
- **One worker.** The end-to-end suite runs one test at a time (`workers: 1`) against one
  server, its deployments shared between tests; `CLOCK_SLUGS` names the clock samples to stop by
  hand, so a new clock sample keeps ticking unless added.
- **A drag in an overlay waits for its view to stop moving.** An overlay fits its view again
  240 ms after it opens, animated over 200 ms (`CompositeOverlay.tsx`), and at its zoom a handle
  is a few pixels wide: a test's `dragTo` begun meanwhile aims where the handle was, and misses.
  "a port added inside a holon takes its first wire's type, and the flow's node gains it" failed
  so 4 runs in 6 until it waited on both handles with `still` (`e2e/samples.e2e.ts`: a box the
  same over two reads 100 ms apart); then 12 in 12 passed (`69494a3`). A new drag in an overlay
  waits the same way.
- **Two editors, two deploy paths.** The terminal editor deploys from `agent::plan`; the web
  editor builds its unit and document through the bridge in `useDeployFlow.ts`. They are meant
  to send the same document ([agent-surface L4](../../L4s/agent-surface-L4.md), decision 5), and
  no test compares them.

## 5. What the tests hold

**Unit tests** (`npx vitest run`, CI job `editor`, after `npx tsc --noEmit -p .`): 24 files; 357
tests when run at `f5f3b39`. Most run against the real wasm core, loaded from `editor/wasm`.

- `samples.test.ts`, `describe("sample flows")`: per sample, "`<name>` builds, derives, and asks
  for exactly what it uses" (one endpoint per `request` template, one clock per `every`, one file
  handler per `on_file`; no capability with `<unknown>` or `Spawn`, which would mean core failed
  closed; each listed secret read; each optional permission used and never the trigger; its `keep`
  and `limit` lines the limits the deploy asks for). Beside them: unique names and ports; a
  manifest listed as the server lists it; a flow nothing starts made runnable by hand; a saved
  flow placed as one node; a holon opened, frozen back unchanged to the same unit, and applied;
  every node described; every sample's text names landing on its canvas.
- `textSync.test.ts` ("the text and the canvas, one flow"): every sample's canvas matches its
  text compiled back; an edit that touches no node keeps every id and place; a changed line keeps
  the others; a deleted line removes its node.
- `textLink.test.ts`: the cursor picks the innermost node; `calc` replayed for a divide by zero
  dims exactly the arms not chosen.
- `replay.test.ts`: a route's group replayed in core's order from recorded inputs; clocks, file
  handlers, outbound calls, secrets, collection reads, choices, durable runs, why a run failed.
- `holonText.test.ts` ("flows as text"), `manual.test.ts` (every link lands, every flow in the
  manual opens), `endpoint.test.ts`, `tallies.test.ts`, `storage.test.ts`, and the rest.

**The built-in editor** (`cargo test -p holon --features embed-editor editor`, job `editor`, after
`npm run build`): `serves_the_page_and_its_files_and_nothing_outside` (no `..`, no API path, no
missing asset) and `the_built_in_editor_is_served`.

**End to end** (`npm run e2e`, Playwright; CI job `e2e`, two shards, `--fully-parallel`, traces
kept on failure). Eight files, 73 tests counted by listing their `test(` calls (one of which makes
a test per eight samples); 72 pass and `atlas-notes` is skipped without `HOLON_TEST_MONGODB`
([Resilience §4](../themes/resilience.md)), in 7.1 minutes at `9969f8b`
([Testing](../themes/testing.md)).

- `samples.e2e.ts`: "the flows page lists every sample" (the titles read from `samples.rs`, so
  none is left out); "samples N to M open from the flows page and deploy", through the consent
  screen; then one test per feature, most replaying a run exactly in view mode.
- `text.e2e.ts`: a mistake marked while the canvas stays, a fix driving the canvas, a node's line
  marked, completion, Format as `fmt` writes, the text saved as typed.
- `agent.e2e.ts`: an agent proposes through `holon mcp`, a person approves in the editor.
- `cli.e2e.ts`, `system.e2e.ts`: the same actions from the command line and over plain HTTP.
- `accounts.e2e.ts`, `home.e2e.ts`, `docs.e2e.ts`: sign-in and roles, the home tab's panes, the
  manual.

**The terminal editor**: `crates/holon/src/workbench/tests.rs`, 22 tests (counted by `#[test]`),
among them `deploying_shows_what_it_may_do_and_deploys_on_enter` and
`a_saved_flow_waits_for_a_person_who_approves_it_from_the_approvals_page`.

Gaps: components drawn only in a browser; the built editor not driven end
to end; the two deploy paths not compared; nothing checks the editor against a server of another
version.
