# P1.5.1 — Encapsulation (derive-then-freeze) · Level-4 design

> **Companion to `PLAN.md`.** The operation that makes the system recursive in practice:
> a selection of wired units becomes a new, hashed `Unit` with an auto-derived interface.
> **Pre:** P1.4.3 (eval), P1.3.1 (validate), the `BOUNDARY` binding. **Inv:** I4
> (derive-then-freeze), I8 (derived, not asserted), I1 (the result is interchangeable with
> the inline computation). **Effort:** M.

---

## 0. The decision that matters: derive vs choose

Encapsulation turns `(children, inner_edges)` into a `Unit`. The crux is **what is
computed from structure versus chosen by the author** — and getting it wrong is expensive
because some of it is *identity* (hashed).

**Derived (computed, never in the spec) — the I8 half:**
- each promoted input's **type** (= the inner port's declared type);
- the exposed output's **type** (= the inner output port's type);
- the **`BOUNDARY` edges** that bind interface to inner graph (generated, §2);
- *(kind = union of children is also derived — but kind is P2; not here.)*

**Chosen (carried in the spec) — genuine authoring decisions:**
- **which** unbound inner inputs to promote (a subset; some may stay unbound);
- their **order** — *this is identity*: the encoder hashes `inputs` as an ordered list, so
  two encapsulations promoting the same ports in different orders are **different units
  with different hashes**. Order cannot be implicit;
- their **names** (the interface port names; a sensible default is the inner port's name);
- **which** inner output to expose (when the selection has more than one free output).

So derive-then-freeze is a **pure function of `(children, inner_edges, spec)`**: the spec
carries exactly the choices, everything else is derived. This keeps the core pure and puts
the choosing in the editor — "one decider," again.

**"Freeze" is not a step.** The derived interface is baked into the hashed `Unit`; by I5 it
cannot drift. Re-deriving from edited children yields a *different* hash, not a mutation.
Constructing-and-hashing *is* the freeze.

## 1. The function and the spec

```rust
pub struct Promote { pub child: u32, pub port: u32, pub name: String }
pub struct EncapSpec { pub promote: Vec<Promote>, pub output: (u32, u32) } // output = (child, port)

pub fn derive_and_freeze(
    children: Vec<Hash>,
    inner_edges: Vec<Edge>,       // child→child only (a self-contained selection)
    spec: &EncapSpec,
    resolver: &impl Resolver,
) -> Result<Unit, EncapError>;
```

Steps:
1. Resolve all children (else `UnresolvedChild`).
2. Validate each `promote`: `child < k`; `port < child.inputs.len()`; the `(child, port)`
   is **not already bound** by an inner edge (promoting a bound port would create a second
   source — the very `DuplicateInputEdge` validation forbids); no duplicate in the list.
3. Validate `output`: `child < k`; `port == 0` (single output); the child's `output` is
   `Some`.
4. **Derive** `inputs`: for each `promote[i]`, `Port { name: promote[i].name, ty: <inner
   (child,port) type> }` — order = spec order.
5. **Derive** `output`: `Some(<inner output type>)`.
6. **Generate** boundary edges (§2) and append to `inner_edges`.
7. Assemble the `Composite` `Unit` (`params: []` — param promotion is P1.5.2).
8. `validate(&unit, resolver)` as a safety net → `EncapError::Invalid` if it ever fails
   (it shouldn't, by construction).

The selection must already be **self-contained and 0-indexed**: extracting and renumbering
a subgraph out of a larger editor graph is the editor's job (P4), not the core's.

---

## 2. Boundary-edge generation — the inverse of eval / validate

P1.4.3 and P1.3.1 *consume* `BOUNDARY` edges; P1.5.1 *produces* them. They must stay in
lockstep, so the generation is exactly the dual of how the evaluator reads them:

- for each `promote[i]` (i = interface input index):
  `Edge { from_child: BOUNDARY, from_port: i, to_child: promote[i].child, to_port: promote[i].port }`
- for the exposed output:
  `Edge { from_child: output.0, from_port: output.1, to_child: BOUNDARY, to_port: 0 }`

These are the edges the evaluator's "inject promoted input" (`BOUNDARY→child`) and "read
exposed output" (`child→BOUNDARY`) already handle. Nothing new in eval; encapsulation just
emits what eval consumes.

---

## 3. `default_spec` — the canonical proposal

The core also offers the deterministic default the editor proposes (and the user may then
reorder / rename / re-point):

```rust
pub fn default_spec(children: &[Hash], inner_edges: &[Edge], resolver: &impl Resolver)
    -> Result<EncapSpec, EncapError>;
```

- **promote** = every **unbound** inner input (no incoming inner edge), in canonical order
  `(child, port)` ascending, each named after its inner port.
- **output** = the unique child whose output is **unconsumed** (no outgoing inner edge); if
  zero or more than one, `AmbiguousDefaultOutput` — the author must choose explicitly.

`default_spec` keeps the canonical order *in the core* (so "encapsulate with defaults" is
reproducible and hash-stable), while `derive_and_freeze` honors any spec verbatim.

## 4. Sub-leaves (build order)

| # | sub-leaf | gist |
|---|---|---|
| a | `EncapSpec` + `EncapError` | the spec/choice types and the error set |
| b | `derive_and_freeze` | validate spec → derive types → generate boundary edges → assemble → validate |
| c | `default_spec` | unbound-inputs (canonical order) + unique free output |

---

## 5. Tests (the proofs)

- **Behavior preservation (the key one):** evaluate a selection inline, then
  `derive_and_freeze` it and evaluate the resulting unit with the same inputs → **identical
  result**. Encapsulation changes identity, not behavior (ties to I1).
- **Interface derived, not asserted:** the promoted inputs' types and the output type match
  the inner ports; the author supplied only names/order.
- **Order is identity:** two specs promoting the same ports in different orders produce
  **different hashes**.
- **`default_spec` canonical:** promotes all unbound inputs in `(child, port)` order; exposes
  the unique free output; `AmbiguousDefaultOutput` when there are two free outputs.
- **Rejections:** promoting a bound port; out-of-range promote/output; non-zero output port.
- **The derived unit always `validate`s.**

## 6. Follow-on: `Map` + the eval `ctx`

`Map` (the 21st primitive) lands right after this leaf, because its function argument is a
**unit reference** — meaningful only once flows can be packaged as referenceable units.

- **`Map` shape:** input `[list]`, param `fn` = hex hash of the unit to apply, output
  `List`. For each element, apply `fn`; `None` if any application is `None`.
- **The `ctx` extension:** `compute` gains an evaluation context —
  `compute(name, inputs, params, ctx)` where `ctx.apply(&Hash, &[Value]) -> Option<Value>`
  resolves the hash and recursively evaluates. The **evaluator is the provider** of that
  context (it already holds the resolver and the recursion). First-order primitives ignore
  `ctx`; only `Map` (and later `Filter`/`Reduce`) use it.

This is a separate small inch (`P1.5.1 → Map → P1.5.2`), noted here so the eval/ctx seam is
designed alongside encapsulation rather than bolted on.

---

## 7. Deferred forks (recorded)

- **Param promotion** — promoting a child's param to the composite interface is **P1.5.2**
  (touches the encoder); P1.5.1 leaves `params` empty.
- **Kind = union of children** — derived, but kind is **P2.2.1**; not computed here.
- **Multi-output composites** — single exposed output only (`port 0`).
- **Unbound-and-unpromoted inputs are allowed** — a composite may carry an internally
  absent input; `default_spec` never produces one (it promotes all unbound), but an explicit
  spec may.
