# Databases on the host

A flow can read and write a database, but only one an admin has bound to a name, and only by
that name. The flow says `database shop`; the admin decides that `shop` is `/srv/shop.db`, or the
shop's Postgres, and what its tables are. The flow never sees where it is, runs no DDL, and is
granted each table its SQL touches (each collection its calls name), no more.

A database is a SQLite file on the server's machine, or a Postgres or MySQL database the server
connects to: the flow's SQL is the same on each. Or it is a MongoDB (a cluster on MongoDB Atlas,
or a replica set of your own), which a flow calls with records instead of SQL
([Documents](#documents-mongodb)).

## Binding a database

An admin binds databases from the editor's **admin** page (**databases**), or on the server's
machine:

```sh
holon database add shop ~/shop.db --schema "create table orders (id integer primary key, customer text not null, total numeric not null, refunded integer not null default 0)"
holon database add reports /srv/reports.db --read-only
holon database list
holon database remove shop
```

| Option | |
|---|---|
| `--schema SQL`, `--schema-file FILE` | run this first (`create table …`), creating the file if there is none |
| `--read-only` | flows may read it, not write it |
| `--lock run` | each run that touches it holds it for its whole length ([Held for whole runs](#held-for-whole-runs)) |
| `--for SLUG` | for that deployment only: it sees this database as the name, and no other deployment sees it |

- A name is letters, digits, `-` and `_`, up to 64 characters.
- Without a schema, the file must already be a SQLite database.
- The server's own data folder can't hold one.
- A writable database gets a table `holon_commits`, where each run that writes marks itself done
  (see below). Flows can't read or write it.
- Removing a binding leaves the file where it is; deployments that use it stop until it is bound
  again.

A deploy is refused until each database the flow names is bound, and bound read-write where the
flow writes.

### Postgres and MySQL

A Postgres or MySQL database is bound by where the server fetches its URL from, as a secret's
value is: one of the server's environment variables named `HOLON_SECRET_…` (or a line of its
`--dotenv` file), or a field in Vault.

```sh
export HOLON_SECRET_SHOP_URL='postgres://shop:…@db.internal:5432/shop'
holon serve
holon database add shop env:HOLON_SECRET_SHOP_URL --schema-file shop.sql
holon database add ledger vault:secret/payments/ledger#url --read-only
```

- The URL (`postgres://user:password@host:port/database`, `mysql://…`) is never stored, shown or
  logged: the binding keeps `env:HOLON_SECRET_SHOP_URL`, and where it points without its
  credentials (`postgres://db.internal:5432/shop`), which is what the admin page and
  `holon database list` show.
- The server connects when it is bound, so a binding that can't connect says why then.
- TLS: Postgres as `?sslmode=` says (`prefer` if not given: TLS where the server offers it), MySQL
  as `?ssl-mode=` says (`REQUIRED` or `DISABLED`; if not given, TLS unless the database is on the
  same machine). Certificates are checked against the public CAs.
- The schema is the engine's own SQL: an id it numbers itself is
  `integer generated by default as identity primary key` on Postgres and
  `integer primary key auto_increment` on MySQL.
- Connect as a role with only what the flows need (`select` on what they read, `insert`,
  `update`, `delete` on what they write), so the database refuses the rest too.
- A writable MySQL database also gets a table `holon_claims` (see
  [Calling out](#calling-out-between-a-read-and-a-write)).

### MongoDB

A MongoDB is bound the same way, by where its URL is fetched from: Atlas's `mongodb+srv://`
address, or `mongodb://` for one of your own. The URL names the database: Atlas's "Connect"
gives one without, ending `.mongodb.net/?…`, so put the name after the `/`. It also gives
`<db_password>` where the password goes: a URL bound with that (or another provider's
`[YOUR-PASSWORD]`) still in it is turned away, saying so, before it is tried.

```sh
export HOLON_SECRET_NOTES_URL='mongodb+srv://notes:…@cluster0.example.mongodb.net/notes'
holon serve
holon database add notes env:HOLON_SECRET_NOTES_URL
```

- No `--schema`: a collection is made as documents are written to it, and its indexes (a unique
  one, say) are made in MongoDB, by the admin.
- A run's writes land in one transaction, which needs a replica set or a sharded cluster: Atlas
  always is one; a server of your own runs with `--replSet` (a replica set of one node is fine).
  A database bound read-write, or set to `--lock run`, is checked for one when it is bound.
- It gets two collections, `holon_commits` and `holon_claims`, which flows can't read or write; a
  flow's collection is letters, digits, `_`, `-` and `.`, and never `system.…`.
- TLS as the URL says (`mongodb+srv://` always has it), checked against the public CAs. The user
  needs only `readWrite` on the database (`read` for one bound `--read-only`).

## Reading and writing

```holon
flow orders-api
port 8150
database shop

route POST /orders (req) {
  shop.exec("insert into orders (customer, total) values ($1, $2)", req.json.customer, req.json.total)
  respond { placed: req.json.customer }, status: 201
}

route GET /orders/:customer (req) { respond shop.query("select id, total, refunded from orders where customer = $1 order by id", req.params.customer) }
```

| Written | Is |
|---|---|
| `db.query(sql, v1, v2, …)` | the rows, as a list of records, as the run began |
| `db.one(sql, v1, …)` | the first row, or no value when there is none (a route answers 404) |
| `db.exec(sql, v1, …)` | run the statement (`insert`, `update`, `delete`) when the run finishes |
| `db.exec(sql, v1, …, expect: n)` | the same, only if it changes exactly `n` rows: else nothing the run wrote lands, and a route answers 409 |

- The SQL is written as text in the flow, because its tables are what the deployment is granted:
  `select … from orders` asks `DbRead("shop/orders")`, `update orders …` asks
  `DbWrite("shop/orders")`. SQL from a value is an error that says so, and so is a statement that
  names no table.
- Values go in after the SQL, as `$1`, `$2`, …; never into its text. The count must match.
- A number crosses as a number, `true`/`false` as 1/0 (as `true`/`false` to a Postgres boolean),
  no value as `null`, a record or list as its JSON text. A column that is `null` is a missing
  field; an integer past 2^53 comes back as text, a blob as hex.
- On Postgres and MySQL, an exact decimal (`numeric`, `decimal`) comes back as text (`"12.50"`),
  so a total is never rounded; a date or time as RFC 3339 text, in UTC; `json` as a value; a
  boolean as `true`/`false`. A column of another type fails the read, saying to cast it
  (`::text`).
- Reads are of the database as the run began; writes land when it finishes, all of them or none.

### Documents (MongoDB)

```holon
flow atlas-notes
port 8154
database notes

route GET /notes/:owner (req) {
  respond notes.find("notes", { owner: req.params.owner, done: false }, sort: { _id: 1 }, limit: 50)
}

route PUT /notes/:owner/:id (req) {
  notes.update("notes", { _id: req.params.id, owner: req.params.owner }, { "$set": { text: req.json.text }, "$inc": { edits: 1 } }, expect: 1)
  respond { edited: req.params.id }
}
```

| Written | Is |
|---|---|
| `db.find("coll", { … }, sort: { … }, limit: n)` | the documents the filter selects, as a list of records, as the run began (no filter: all of them) |
| `db.find_one("coll", { … }, sort: { … })` | the first, or no value when there is none (a route answers 404) |
| `db.insert("coll", { … })` | add the document when the run finishes |
| `db.update("coll", { filter }, { "$set": { … } }, expect: n)` | apply the update (`$set`, `$inc`, `$push`, … ) to the documents the filter selects |
| `db.delete("coll", { filter }, expect: n)` | delete the documents the filter selects |

- The collection is written in quotes, as SQL is, because it is what the deployment is granted:
  `notes.find("notes", …)` asks `DbRead("notes/notes")`; an insert, `DbWrite`; an update or a
  delete, both.
- The filter, the update, the document and the sort are **records written in the call**: their
  fields and operators (`$in`, `$gt`, `$set`, …) are the flow's, fixed when it is deployed, and
  each value computed from the request goes in as data, never as an operator. A record given as a
  value with a field starting with `$` (a request's `{"$ne": null}`) fails the run, and nothing it
  did lands. A record from a value (`notes.find("notes", f)`) or a spread is an error that says
  so, and so are `$where`, `$function` and `$accumulator`, which run code on the server; an update
  is operators only, a sort fields of `1` and `-1`.
- `expect: n` on an update counts the documents its filter matched, on a delete those it
  deleted: else nothing the run wrote lands, and a route answers 409. An insert whose `_id` is
  there already answers 409 too.
- Values cross as JSON does: a whole number as an integer, a record as a document, a list as an
  array, no value as `null`. `{ "$oid": v }`, `{ "$date": v }`, `{ "$numberDecimal": v }` and
  `{ "$numberLong": v }` make `v` an id, a date (RFC 3339 text), an exact decimal or a long.
- Back, a document is a record by field: an id as its hex, a date as RFC 3339 text (UTC), a
  decimal as text, a long past 2^53 as text, bytes as hex; a `null` field is missing. A field of
  another type fails the read, saying to leave it out.

## When runs touch the same rows

A run's reads and its writes are one step. When the run finishes, the server opens a transaction
on each database it wrote, reads again what the run read, and lands the writes only if it is all
as the run found it. If another run changed it in between, the run runs again, on what is there
now (four times, then once more holding the database so that no other run can change it). Two
deployments counting in one row lose no count.

`expect:` is for the change that must happen once: refund an order only if it isn't refunded yet.

```holon
flow refunds
port 8151
database shop

route POST /order/:id/refund (req) {
  shop.exec("update orders set refunded = 1 where id = $1 and refunded = 0", req.params.id, expect: 1)
  respond { refunded: req.params.id }
}
```

The second refund changes no row: the run fails with `changed 0 rows, not 1 row`, writes
nothing (here or anywhere else), and answers 409.

The same transaction inserts the run's id into `holon_commits`, so a database says itself which
runs landed in it.

On Postgres and MySQL the transaction is `serializable`, so this holds for several servers on one
database too: two runs of different servers that each read what the other writes can't both
commit, and the one that can't runs again. A deadlock, or a lock not had within
`commit_wait_ms`, sends a run round again the same way. The check also sees a change another
program made, as long as it was made before the check: on MySQL what the check read stays locked
until the commit; on Postgres, a program that writes in the milliseconds between them isn't
seen.

On MongoDB the commit is a transaction too, reading a snapshot: a document it writes that another
writer changed since makes MongoDB end it, and the run goes round again. A document it only reads
that a program outside Holon changes in the milliseconds between the check and the commit isn't
seen; Holon's own runs, of any server, are held off by claims ([below](#calling-out-between-a-read-and-a-write)).

## Calling out between a read and a write

Running again is safe for what a run writes, not for what it sends: a run that read an order,
called a payment API and then found the order changed would have paid twice by the time it ran
again. So a run that reads a row it may write, and then calls out, **holds the row** from its
first outbound call until it commits. Another run that read the same row waits at its own first
call; when the row is let go, it reads it again, and runs again on what it finds, having sent
nothing.

```holon
flow refund-once
port 8151
database shop

route POST /refund/:id (req) {
  order = shop.one("select id, total from orders where id = $1 and refunded = 0", req.params.id)
  paid = http.post("httpbin.org", "/anything/refunds", headers: { "content-type": "application/json" }, body: json({ order: order.id, amount: order.total }))
  shop.exec("update orders set refunded = 1 where id = $1 and refunded = 0", order.id, expect: 1)
  shop.exec("insert into refunds (order_id, amount, status) values ($1, $2, $3)", order.id, order.total, paid.status)
  respond { refunded: order.total, payment: paid.status }, missing: 409
}

route GET /refunds/:id (req) {
  respond shop.query("select amount, status from refunds where order_id = $1", req.params.id)
}
```

Two refunds of one order at once call the payment API once: the second finds the order refunded,
its query answers no row, nothing after it runs, and it answers 409. The `refund-once` sample
shows it beside `orders-api`, on the same database.

- A read whose `where` sets the table's whole primary key equal to values (`id = $1`, with other
  conditions joined by `and`) holds that row. Any other read of a table it may write (a range, a
  join, a count) holds the whole table, which waits for every row under it.
- An insert waits only for a run holding the whole table; one that gives the primary key waits
  for that row too.
- Holding is across deployments: every deployment bound to the database sees the same rows held,
  whatever name it knows the database by.
- On Postgres and MySQL, across servers too: the rows are held in the database itself (Postgres
  advisory locks; on MySQL, locks on rows of `holon_claims`), on a connection of their own, so
  a server that stops lets go of them with its connection.
- On MongoDB the same, in the database's `holon_claims` collection: a document a filter names by
  `_id` (an insert, by its document's `_id`) is held alone, any other call holds the collection.
  Each is held with a 30-second lease the server renews while the run lasts, so a server that
  stops lets go within 30 seconds.
- A run that never calls out holds nothing; one that only reads a table holds nothing in it.
- `holon check` says it, under `while it runs:`, and the run log lists each row held, how long it
  waited, and whether it found the row changed. A run waits `claim_wait_ms` at most (10 s).

## Runs that wait

A run that waits for an event (`await`) holds nothing while it waits: a row it read is anyone's
to change until the event comes. When it does, the run goes on from where it waited, its own
state as it first found it, and its databases and files **as they are now**: it reads them again.
Its commit checks those reads as any run's does, and holds what it reads before it calls out, so
if a row changed again in between, it runs again from where it waited, its requests and the
event answered from its record, not sent or asked again.

```holon
flow approved-payout
port 8153
database bank

route POST /payout/:account (req) {
  account = bank.one("select id, balance from accounts where id = $1", req.params.account)
  respond { approve: "/approve/{resume_token(approved)}", balance: account.balance }, status: 202
  approved = await approved, expires: 1d
  sent = http.post("httpbin.org", "/anything/payouts", headers: { "content-type": "application/json" }, body: json({ account: account.id, amount: req.json.amount, by: parse_json(approved.body).by }))
  bank.exec("update accounts set balance = $1 where id = $2", account.balance - req.json.amount, account.id, expect: 1)
  bank.exec("insert into payouts (account, amount, status) values ($1, $2, $3)", account.id, req.json.amount, sent.status)
}

route POST /approve/:token (req) resumes approved {
  respond "approved"
}
```

- A deposit made while the payout waits for its approval is kept: the approved run reads the
  balance with the deposit in it.
- One made while the payout is being sent waits for the row the run holds, and runs again on
  the balance the run wrote.
- One made by a program outside Holon at that moment is found by the run's commit: the run goes
  round again from its approval, on the new balance, and its payout isn't sent again.

## Held for whole runs

The check at commit, and holding what a run read before it calls out, let runs go side by side
and keep them right. Some things they can't make right, or only by running a lot again: a
sequence many runs take the next number of at once, a queue, an API with no transactions that
must see one caller at a time. For those an admin sets the database to be **held for whole
runs**:

```sh
holon database add tickets ~/tickets.db --lock run --schema-file tickets.sql
```

- Each run that touches it takes it **before it starts**: shared if its flow only reads the
  database, alone if it may write it (what its manifest says, not what one run happens to do).
  It holds it until it commits, fails or waits for an event.
- So **every run that writes it goes one at a time, for its whole length**, across every
  deployment bound to it, and on Postgres, MySQL or MongoDB across every server (the lock is held
  in the database, as claims are). Runs that only read it go side by side, after any writer.
- A run that would wait past `claim_wait_ms` (10 s) for it is turned away: a request answers 503
  naming the database, a clock tick is skipped; both are in the run log, and nothing was sent.
- Nothing in the flow changes: the same text runs on a database held only across commits.
- The `ticket-numbers` sample shows it: twenty requests at once take twenty numbers one after the
  other, each run committing on its first try.

It is off unless set: it costs every writer its turn, where the check costs a run going again
only when two touched the same rows. A folder can be set so too (`holon folder add … --lock run`).

## Limits

| Name | Is | Default | Ceiling |
|---|---|---|---|
| `max_db_rows` | rows a run reads in all | 10000 | 1000000 |
| `max_db_read_bytes` | bytes a run reads in all | 16777216 (16 MiB) | 268435456 |
| `db_statement_ms` | time one statement may take | 5000 | 60000 |
| `max_db_statements` | statements a run sends, reads and writes | 100 | 10000 |

A read past a limit fails the run, and it writes nothing. A deployment that needs more asks for
it, as with every limit ([Permissions](../reference/permissions.md#limits)).

## What the run log keeps

Each read is in the run's log with its answer, so `holon verify` runs it again offline, with no
database: the same rows give the same answer. A run that failed (an unmet `expect:`) wrote
nothing and is skipped.
